# Athena 双端系统功能设计说明

## 1. 文档定位

本文档用于说明 Athena 双端系统的功能设计方案，重点描述系统功能边界、模块划分、角色权限、业务流程、数据对象、状态流转、异常处理和扩展约束。

本文档与《使用手册.md》的区别如下：

- 《使用手册.md》面向最终使用者，强调页面入口、操作步骤、使用注意事项和截图说明。
- 本文档面向开发、测试、答辩、维护和交付评审人员，强调功能为什么这样设计、模块之间如何协作、数据如何流转、功能验收应关注哪些结果。
- 本文档不逐步讲解“点击哪个按钮”，而是说明系统能力、业务规则和设计逻辑。

## 2. 系统功能总览

Athena 系统由管理员网站端 `admin_web_front` 和用户 App 端 `athena_app_front` 组成。两端围绕同一套内容、用户、健康记录和 AI 服务能力协同工作。

### 2.1 管理员网站端定位

管理员网站端负责平台运营侧能力，主要解决内容生产、内容审核、内容治理和后台协作问题。其核心目标是保证平台内容可控、发布流程清晰、审核责任明确、违规内容可处理。

核心功能包括：

- 登录认证与角色权限控制
- 内容审核列表与审核详情
- 内容驳回与删除处理
- 内容管理与筛选检索
- 文章发布与视频发布
- 文件上传与富文本编辑
- 系统设置与后续扩展入口

### 2.2 用户 App 端定位

用户 App 端负责面向普通用户提供女性健康服务，主要解决内容消费、社区互动、智能咨询、健康记录、隐私保护和个人资料管理问题。

核心功能包括：

- 登录注册与本地登录状态维护
- 推荐页与知识内容浏览
- 社区广场、图文详情、视频详情与互动
- App 端内容发布入口
- AI 问答与科普检索
- 经期记录、身体状况记录、备孕相关记录
- 分析报告与健康趋势展示
- 隐私守护、私密图库和敏感信息处理
- 个人中心、资料编辑、关注与粉丝关系

### 2.3 双端协同关系

Web 端与 App 端不是两个孤立系统，而是围绕内容生命周期形成闭环。

典型协同链路：

1. 内容发布者在 Web 端创建文章或视频。
2. 内容进入审核或管理流程。
3. 管理员在 Web 端审核、驳回、删除或维护内容。
4. 审核通过或已发布内容进入 App 推荐、知识或广场内容流。
5. App 用户浏览、互动、收藏、评论或继续发布内容。
6. 用户产生的社区内容再次进入后台治理范围。

## 3. 用户角色与权限设计

### 3.1 角色划分

系统按职责划分为三类主要角色。

| 角色 | 使用端 | 职责定位 | 主要功能 |
| --- | --- | --- | --- |
| 管理员 | Web 端 | 平台治理与内容审核 | 审核、驳回、删除、内容管理、设置 |
| 内容发布者 | Web 端 | 平台内容生产 | 发布文章、发布视频、查看发布结果 |
| 普通用户 | App 端 | 内容消费与健康记录 | 浏览、互动、发布、AI 咨询、记录、个人中心 |

### 3.2 权限控制原则

权限设计遵循最小授权原则，即用户只能访问完成自身职责所需的功能。

Web 端权限控制设计：

- 未登录用户只能访问登录页。
- 已登录用户携带鉴权凭证访问受保护页面。
- 管理员角色可访问审核、内容管理、删除处理和设置类能力。
- 内容发布者角色可访问内容发布相关页面。
- 路由层与接口层均应校验登录状态，避免仅依赖页面隐藏按钮实现权限控制。

App 端权限控制设计：

- 未登录用户可进入登录注册流程。
- 登录状态持久化后，App 展示底部主导航与个人服务入口。
- 需要用户身份的数据，例如发布、评论、个人资料、健康记录，应在调用接口前校验登录态。
- 涉及相册、相机、文件、网络和隐私处理的功能，应在使用前完成系统权限申请和用户授权提示。

### 3.3 权限异常处理

当鉴权失败或角色不匹配时，应采用明确的失败策略：

- 登录过期：跳转登录页或提示重新登录。
- 权限不足：提示无权访问当前功能。
- 接口拒绝：保留页面结构，展示错误信息，不应出现空白页。
- 关键操作失败：保留用户输入，避免因失败导致内容丢失。

## 4. 内容中心功能设计

内容中心是 Athena 双端系统的核心业务域，覆盖内容创建、审核、发布、展示、互动和治理。

### 4.1 内容类型设计

系统内容主要分为文章、图文动态和视频三类。

| 内容类型 | 主要载体 | 典型使用场景 | 关键字段 |
| --- | --- | --- | --- |
| 文章 | 标题、正文、封面、分类 | 健康科普、平台知识库、专题内容 | 标题、正文、分类、封面、作者、状态 |
| 图文动态 | 文本、多图、作者信息 | 社区分享、经验交流、生活记录 | 文本、图片列表、作者、互动数、状态 |
| 视频 | 视频文件或地址、封面、简介 | 科普视频、社区视频、运营内容 | 标题、视频地址、封面、简介、作者、状态 |

内容对象应具备统一的基础属性：

- 内容 ID
- 内容标题或摘要
- 内容类型
- 所属模块或分类
- 作者或发布者
- 创建时间、更新时间
- 审核状态
- 展示状态
- 封面、图片或视频资源地址

### 4.2 内容状态设计

内容状态用于控制内容从创建到展示再到治理的完整生命周期。

建议状态包括：

| 状态 | 含义 | 可见范围 |
| --- | --- | --- |
| 草稿 | 内容尚未正式提交 | 发布者本人 |
| 待审核 | 内容已提交，等待管理员处理 | 发布者、管理员 |
| 已通过 | 内容审核通过，可进入展示流程 | 管理员、App 用户 |
| 已驳回 | 内容不符合规则，需要修改 | 发布者、管理员 |
| 已删除 | 内容被管理员移除 | 管理员或系统记录 |
| 已下架 | 内容保留但不对用户展示 | 管理员 |

当前项目页面已覆盖待审核、详情查看、驳回、删除、内容管理和发布能力。若后续扩展草稿箱、下架、定时发布等能力，应在该状态模型上扩展，不建议新增彼此冲突的状态字段。

### 4.3 内容审核设计

内容审核模块用于降低不合规内容进入用户侧的风险。审核设计应同时满足效率和可追溯性。

功能边界：

- 展示待审核内容列表。
- 支持查看内容详情。
- 支持根据内容类型、模块、状态等条件筛选。
- 支持审核通过、驳回或删除处理。
- 支持展示封面、正文、视频等关键审核材料。

设计要点：

- 列表页用于快速定位内容，详情页用于最终判断。
- 审核操作应绑定具体内容 ID，避免仅依赖列表位置。
- 驳回必须记录原因，便于发布者修改，也便于后续运营复盘。
- 删除属于高风险操作，应具备确认机制。
- 审核结果应同步影响 App 端内容可见性。

### 4.4 内容管理设计

内容管理模块面向已入库内容的持续维护，不只服务“审核前”，也服务“发布后”。

功能边界：

- 查看全量或指定范围内容。
- 按类型、分类、模块、状态等维度筛选。
- 查看内容详情。
- 对违规、重复、错误内容进行删除或下架。
- 为运营排查提供内容定位能力。

与审核模块的区别：

- 审核模块关注“内容能否发布”。
- 内容管理模块关注“内容发布后是否仍然适合保留和展示”。
- 审核模块偏流程处理，内容管理模块偏资产维护。

### 4.5 内容发布设计

Web 端发布模块面向内容发布者，负责标准化采集文章和视频的必要信息。

文章发布设计：

- 标题字段用于内容识别和列表展示。
- 分类字段用于推荐、知识模块或广场内容归类。
- 正文字段支持富文本编辑，便于承载长篇科普内容。
- 封面或配图用于 App 内容卡片展示。
- 提交后进入审核或内容管理流程。

视频发布设计：

- 视频标题用于搜索和列表展示。
- 视频简介用于说明内容主题。
- 视频文件或视频地址作为核心资源。
- 封面图用于提升内容识别度。
- 提交后应校验视频资源可用性。

文件上传设计：

- 上传能力应与文章、视频、用户头像、社区图片等场景复用。
- 前端应限制明显不符合要求的文件类型和大小。
- 上传失败时应提示原因，并允许用户重新选择文件。
- 上传成功后应保存资源地址，而不是将大文件直接塞入业务字段。

### 4.6 App 内容展示设计

App 端内容展示围绕推荐页、知识模块和广场模块组织。

推荐页设计：

- 作为用户进入 App 后的内容发现入口。
- 可承载平台推荐内容、健康知识、社区内容和横幅信息。
- 应优先展示标题、封面、摘要、作者或来源等快速判断信息。

知识模块设计：

- 面向结构化健康科普内容。
- 按年龄阶段、健康主题或生活场景组织分类。
- 适合承载经过审核、相对稳定、可长期复用的内容。

广场模块设计：

- 面向社区互动内容。
- 支持图文和视频内容流。
- 应突出作者信息、发布时间、互动数据和内容摘要。
- 需要与评论、点赞、收藏、关注等用户行为联动。

详情页设计：

- 图文详情页负责完整展示文本、图片和评论区域。
- 视频详情页负责播放视频并展示互动入口。
- 详情页应根据内容状态处理不可见、已删除、加载失败等情况。

## 5. AI 功能设计

AI 模块是用户端的智能辅助能力，主要用于健康问题问答、知识检索辅助、内容理解和隐私守护。

### 5.1 AI 问答设计

功能边界：

- 接收用户自然语言输入。
- 返回结构化或自然语言形式的回答。
- 支持历史会话或上下文展示。
- 支持关联知识内容作为参考材料。

设计原则：

- 回答应定位为健康信息参考，不应替代医生诊断。
- 对用药、急症、严重症状等高风险问题，应提示用户咨询专业医生。
- 输入框与消息列表应明确区分用户消息和 AI 消息。
- 请求处理中应展示加载状态，避免用户重复提交。
- 请求失败时应允许重试。

### 5.2 科普检索辅助设计

科普 AI 用于帮助用户从知识内容中更快找到相关信息。

功能边界：

- 根据用户问题检索相关科普内容。
- 将回答与知识卡片、参考文章或推荐内容关联。
- 支持从知识模块跳转到 AI 搜索或问答。

设计要点：

- AI 回答和知识内容应形成互补：AI 负责解释，知识内容负责提供可复查的信息来源。
- 对用户输入应做基本清洗，避免空问题、重复提交或过长文本影响体验。
- 推荐内容应与当前问题相关，避免泛化推荐。

### 5.3 隐私守护 AI 设计

隐私守护模块用于降低用户在咨询、发布和上传过程中暴露敏感信息的风险。

功能边界：

- 对用户输入文本进行敏感信息提醒。
- 对图片上传、私密图库或报告类内容提供隐私处理入口。
- 支持本地脱敏、遮挡、模糊、OCR 识别或上传前确认等能力扩展。

设计原则：

- 优先在本地完成可本地处理的隐私操作。
- 上传前给出明确提示，让用户知道哪些数据会被处理。
- 避免在 UI 中明文展示高敏感内容。
- 对隐私相关操作应强调用户确认，而不是默认静默上传。

## 6. 健康记录与分析功能设计

健康记录模块是 App 端区别于普通内容社区的重要能力，负责收集用户自愿记录的周期和身体状态数据，并生成辅助分析结果。

### 6.1 经期记录设计

功能边界：

- 记录经期开始日期和结束日期。
- 展示周期日历。
- 标记经期、预测期、排卵期等状态。
- 支持周期设置或周期相关参数维护。

核心数据：

- 用户 ID
- 记录日期
- 经期开始日期
- 经期结束日期
- 周期长度
- 经期长度
- 备注或状态标签

设计要点：

- 经期记录应允许用户修正历史数据。
- 预测结果应与真实记录区分展示。
- 周期计算应基于连续记录，数据不足时不应过度给出确定性结论。
- 记录保存失败时应提示用户，避免误以为已记录成功。

### 6.2 身体状况记录设计

身体状况记录用于补充经期之外的健康事件，使系统具备更完整的个人健康观察能力。

记录类型可包括：

- 症状记录
- 情绪记录
- 睡眠或习惯记录
- 体温、体重等身体指标
- 分泌物、疼痛、用药等特殊状态
- 备孕、排卵试纸、HCG、孕期检查等扩展记录

设计要点：

- 不同记录类型可共用日期、类型、数值、备注等基础结构。
- 对强结构化数据使用固定字段，对开放描述使用备注字段。
- 记录入口应保持统一，减少用户理解成本。
- 后续分析报告应能够读取这些记录形成趋势判断。

### 6.3 备孕与周期扩展设计

项目中包含备孕、排卵、孕期和相关健康指标入口，因此记录模块应支持从单一经期记录扩展为生命周期健康记录。

设计方向：

- 经期模式关注周期、经期、排卵预测。
- 备孕模式关注排卵、同房、试纸、体温、检查记录。
- 孕期模式关注孕周、产检、胎动、体重、血糖等指标。
- 模式之间应复用日历、记录、报告等基础能力。

### 6.4 分析报告设计

分析报告用于将离散记录转化为可阅读的阶段性概览。

功能边界：

- 汇总周期、经期、身体状态等数据。
- 展示趋势、阶段、提示和异常关注点。
- 提供面向用户的健康观察建议。

设计原则：

- 报告应说明依据来自用户记录，而不是绝对医学判断。
- 数据不足时应提示“记录不足”，不应生成过度确定的结论。
- 异常提示应谨慎表达，建议用户必要时咨询专业人员。
- 报告页面应支持后续扩展，例如按月、按周期、按备孕阶段生成。

## 7. 社区互动功能设计

社区互动围绕广场内容、详情页、评论、点赞、收藏、关注关系展开。

### 7.1 内容流设计

内容流是社区浏览的主入口，应解决“用户快速发现感兴趣内容”的问题。

设计要点：

- 卡片应展示足够的判断信息，例如封面、标题、作者、互动数。
- 图文和视频可使用不同卡片样式，但数据模型应尽量统一。
- 列表加载应支持刷新、分页或增量加载。
- 空状态、加载失败和无更多内容应有明确反馈。

### 7.2 互动设计

互动能力包括评论、回复、点赞、收藏、关注等。

设计原则：

- 点赞、收藏属于轻量状态变更，应及时反馈。
- 评论和回复属于内容生产，应校验登录状态和输入合法性。
- 关注关系影响个人中心、关注列表和粉丝列表。
- 互动数据应与详情页和列表页保持一致。

### 7.3 App 端发布设计

App 发布入口主要服务用户社区内容生产，与 Web 端发布不同。

区别说明：

- Web 端发布偏正式内容生产，常用于平台文章和视频。
- App 端发布偏用户社区分享，常用于图文动态或用户视频。
- 两者都应进入内容治理体系，但字段完整性、审核规则和展示位置可以不同。

App 发布设计要点：

- 支持图文内容和视频内容的发布入口。
- 支持图片选择、视频选择、文本输入和基础校验。
- 提交后应进入可追踪状态，避免用户不清楚内容是否提交成功。
- 发布前可接入隐私守护能力，提示用户检查敏感信息。

## 8. 个人中心与用户资料设计

个人中心承担用户身份、个人内容、社交关系和设置入口的聚合职责。

### 8.1 个人中心首页

功能边界：

- 展示用户头像、昵称和基础资料。
- 展示关注、粉丝、发布内容等个人数据入口。
- 提供个人信息编辑、隐私功能、设置等入口。
- 承接用户与系统的账号级交互。

设计要点：

- 个人中心应区分公开资料和仅本人可见资料。
- 用户未登录时应引导登录，而不是展示错误数据。
- 数据加载失败时应保留页面结构并提供重试。

### 8.2 个人信息编辑

个人信息编辑用于维护用户基础资料。

字段可包括：

- 头像
- 昵称
- 性别或身份标签
- 生日或年龄阶段
- 简介
- 其他扩展资料

设计原则：

- 公开展示字段应明确。
- 敏感字段应减少采集或限制展示。
- 修改后应同步刷新个人中心和内容作者信息。
- 上传头像时应复用文件上传能力。

### 8.3 关注与粉丝关系

关注关系用于构建社区社交连接。

功能边界：

- 查看关注列表。
- 查看粉丝列表。
- 关注或取消关注用户。
- 在个人主页、内容详情或列表中展示关注状态。

设计要点：

- 关注状态应防止重复提交。
- 关注数量和粉丝数量应与列表数据保持一致。
- 被删除或异常用户应有兜底展示策略。

## 9. 隐私与安全功能设计

Athena 涉及女性健康、经期、身体状况、图片、报告和 AI 咨询内容，隐私设计是系统重要组成部分。

### 9.1 敏感数据范围

系统应重点保护以下数据：

- 登录凭证和用户身份信息
- 头像、昵称、生日等个人资料
- 经期、备孕、身体状况和健康报告
- 用户发布的图片、视频和私密图库内容
- AI 咨询文本和可能包含隐私的信息
- OCR 识别结果和上传前处理数据

### 9.2 隐私处理原则

- 最小采集：只采集完成功能所必需的数据。
- 明确告知：涉及上传、分析、AI 处理时给出清晰提示。
- 本地优先：可本地完成的脱敏、模糊、遮挡优先在本地完成。
- 最小展示：敏感数据不在无关页面展示。
- 可控提交：用户应能确认是否继续上传或发布。

### 9.3 私密图库与图片处理

私密图库和图片隐私处理用于管理用户不适合公开展示的图片资料。

设计要点：

- 图片预览、选择、保存和上传应区分。
- 上传前应允许用户确认处理结果。
- OCR 或 AI 分析产生的中间结果应谨慎展示和保存。
- 对相册、文件和相机权限应按需申请。

### 9.4 安全边界

前端应负责体验层保护和基础校验，但不能替代后端安全校验。

前端应完成：

- 登录态检查
- 参数合法性检查
- 敏感操作确认
- 权限申请提示
- 错误提示与重试

后端应完成：

- 最终身份鉴权
- 角色权限校验
- 内容状态变更校验
- 文件安全校验
- 数据持久化和审计记录

## 10. 页面与导航结构设计

### 10.1 Web 端页面结构

Web 端采用以登录页和主布局为核心的结构。

主要页面：

- 登录页：负责账号登录和角色识别。
- 主布局：负责导航、页面容器和受保护页面承载。
- 审核页：负责待审核内容列表、审核详情和处理入口。
- 内容管理页：负责内容筛选、详情查看和删除处理。
- 发布中心：负责文章发布、视频发布和发布入口聚合。
- 设置页：负责预留系统配置和扩展能力。

设计要点：

- 受保护页面应统一通过登录态控制。
- 页面间跳转应保持角色边界清晰。
- 管理类页面应优先保证列表可读性、筛选效率和操作确认。

### 10.2 App 端导航结构

App 端采用底部主导航承载核心功能。

主导航包括：

- 推荐或知识入口
- 广场
- AI
- 记录
- 我的

设计要点：

- 主导航用于一级功能切换，不应承载过深流程。
- 详情、发布、编辑、分析报告等页面通过二级页面打开。
- 涉及表单、上传、AI 请求的页面应支持返回和失败恢复。
- 个人中心与设置入口应承载账号级操作。

## 11. 数据流设计

### 11.1 Web 端数据流

登录数据流：

1. 用户提交账号信息。
2. 前端调用登录接口。
3. 接口返回用户身份、角色和鉴权凭证。
4. 前端保存必要登录状态。
5. 路由根据角色进入对应功能页面。

审核数据流：

1. 审核页请求待审核内容列表。
2. 用户选择内容后请求详情数据。
3. 管理员提交审核、驳回或删除操作。
4. 后端更新内容状态。
5. 前端刷新列表和详情状态。

发布数据流：

1. 发布者填写文章或视频信息。
2. 前端进行基础校验。
3. 文件资源先上传并获得资源地址。
4. 前端提交内容主体数据。
5. 后端创建内容记录并进入后续流程。

### 11.2 App 端数据流

内容浏览数据流：

1. App 请求推荐、知识或广场列表。
2. 前端渲染内容卡片。
3. 用户进入详情页。
4. 详情页请求完整内容和互动数据。
5. 用户执行评论、点赞、收藏等操作后同步更新状态。

健康记录数据流：

1. 用户在记录页面录入日期和状态。
2. 前端校验记录字段。
3. 数据保存到本地或通过接口提交。
4. 日历和分析报告读取记录数据。
5. 报告模块生成趋势和提示。

AI 数据流：

1. 用户输入问题。
2. 前端构造请求并展示发送状态。
3. AI 服务返回回答和参考内容。
4. 前端展示回答、参考卡片和错误兜底。
5. 会话内容按设计策略保存或清理。

隐私处理数据流：

1. 用户选择图片或输入文本。
2. 前端执行本地检查、脱敏或遮挡。
3. 用户确认处理结果。
4. 必要时上传处理后的资源。
5. AI 或后端返回分析结果。

## 12. 异常与边界场景设计

### 12.1 网络异常

网络异常时应避免页面静默失败。

处理策略：

- 列表加载失败显示重试入口。
- 表单提交失败保留已输入内容。
- AI 请求失败提示用户重试。
- 上传失败展示失败原因或统一错误提示。

### 12.2 空数据场景

空数据不是错误，应提供明确状态。

场景包括：

- 无待审核内容。
- 无发布内容。
- 无评论或互动数据。
- 尚未记录经期或身体状况。
- 分析报告数据不足。

设计要求：

- 空状态文案应说明当前结果。
- 可提供下一步入口，例如去发布、去记录、刷新列表。

### 12.3 敏感操作

敏感操作包括删除内容、驳回内容、退出登录、上传隐私资料、公开发布健康内容等。

设计要求：

- 操作前确认。
- 操作后反馈。
- 失败时不改变本地展示状态，或在确认后回滚。
- 尽量记录处理原因，便于追踪。

### 12.4 数据一致性

常见一致性问题包括列表状态与详情状态不一致、点赞数延迟、删除后仍可进入详情等。

处理策略：

- 状态变更后刷新当前页面数据。
- 对乐观更新失败的互动操作执行回滚。
- 详情页加载时重新校验内容状态。
- 关键操作以接口返回结果为准。

## 13. 非功能设计要求

### 13.1 可用性

- 核心功能入口应清晰可见。
- 高频操作路径应尽量短。
- 表单错误应定位到具体字段。
- 页面加载、上传、AI 生成等耗时操作应有明确反馈。

### 13.2 性能

- 列表页应支持分页、分批加载或按需加载。
- 图片和视频应避免一次性加载过多资源。
- 富文本、图片预览和视频播放应控制资源占用。
- AI 请求应避免重复提交。

### 13.3 可维护性

- Web 端应按页面、组件、接口、工具函数分层组织。
- App 端应按 Activity、Fragment、Adapter、Service、Model 等职责拆分。
- 通用能力如上传、鉴权、内容模型、分类映射应集中维护。
- 新增模块应同步补充需求、设计、使用和测试说明。

### 13.4 安全性

- Token 不应暴露在页面文本中。
- 角色权限不能只依赖前端隐藏入口。
- 用户输入应进行必要校验。
- 文件上传应校验格式、大小和业务合法性。
- 隐私数据应遵循最小展示和最小上传原则。

### 13.5 可扩展性

系统后续可扩展方向包括：

- 审核记录与审核日志。
- 内容下架、恢复、草稿箱和定时发布。
- 知识内容搜索和专题聚合。
- 更完整的健康报告体系。
- AI 会话历史、个性化问答和知识库增强。
- 隐私处理能力扩展为更完整的图片脱敏工作流。

## 14. 功能验收要点

### 14.1 Web 端验收

- 未登录用户不能访问受保护页面。
- 不同角色登录后进入符合权限的页面。
- 管理员可查看待审核列表和内容详情。
- 管理员可完成驳回、删除等内容处理。
- 内容管理支持查看、筛选和详情核对。
- 发布者可提交文章和视频。
- 上传失败、接口失败、登录过期等异常有明确反馈。

### 14.2 App 端验收

- 用户可完成登录注册并保持登录状态。
- 推荐、知识、广场、AI、记录、我的等主模块可正常切换。
- 图文详情和视频详情可正常展示内容。
- 评论、点赞、收藏、关注等互动功能有状态反馈。
- 经期记录、身体状况记录和分析报告可以形成数据闭环。
- AI 问答有输入、回复、加载和失败处理。
- 隐私守护、私密图库或图片处理相关功能有明确授权和确认过程。
- 个人信息编辑后能同步到个人中心展示。



## 4. RAG 前端功能设计

### 4.1 系统定位

RAG 前端是 Athena 的智能问答知识库管理系统前端应用，采用 React + TypeScript 技术栈，提供用户对话界面和完整的管理后台功能。

核心目标：
- 为终端用户提供流畅的 AI 对话体验
- 为管理员提供知识库全生命周期管理能力
- 支持 RAG 系统的配置、监控和优化

### 4.2 用户端功能设计

#### 4.2.1 智能对话功能

**基础对话能力**：
- 文本消息输入（1-2000 字符限制）
- 实时流式响应（基于 SSE 技术）
- Markdown 内容渲染
- 代码块语法高亮
- 消息历史记录展示

**深度思考模式**：
- 切换开关控制是否启用
- AI 先展示思考过程，再给出最终回答
- 思考内容与回答内容分别展示
- 适用于需要推理分析的复杂问题

**消息交互**：
- 复制消息内容到剪贴板
- 消息反馈（点赞/点踩）
- 停止生成（中断流式输出）
- 查看引用来源（跳转到知识库文档）

**设计要点**：
- 消息发送前校验登录状态和输入长度
- 流式响应通过 EventSource 实现
- 消息状态包括：发送中、生成中、已完成、已失败
- 引用来源以卡片形式展示在消息底部

#### 4.2.2 会话管理功能

**会话生命周期**：
- 创建会话：自动或手动创建新对话
- 查看会话：按时间倒序展示会话列表
- 切换会话：点击会话卡片切换上下文
- 重命名会话：修改会话标题（1-50 字符）
- 删除会话：移除会话及所有关联消息

**会话列表设计**：
- 显示会话标题、最后更新时间
- 当前会话高亮显示
- 鼠标悬停显示操作按钮
- 支持滚动加载历史会话

**会话持久化**：
- 会话 ID 记录在 URL 路径中
- 切换会话时路由同步更新
- 刷新页面时恢复当前会话
- 会话列表实时同步到后端

### 4.3 管理端功能设计

#### 4.3.1 仪表板

**统计数据展示**：
- 知识库总数
- 文档总数
- 会话总数
- 查询量统计

**可视化图表**：
- 查询量趋势图（折线图，近 7 天数据）
- 知识库分布图
- 热门问题排行

**设计要点**：
- 数据来源于后端聚合接口
- 图表使用 Recharts 库实现
- 支持时间范围切换（日/周/月）
- 点击统计数据可跳转到详情页

#### 4.3.2 知识库管理

**知识库 CRUD**：
- 创建知识库：填写名称、描述、选择嵌入模型
- 查看列表：卡片或列表形式展示所有知识库
- 查看详情：显示知识库信息和关联文档
- 删除知识库：确认后删除（级联删除所有文档）

**文档管理**：
- 上传文档：支持 PDF/DOCX/TXT/MD/HTML 格式
- 文件大小限制：单文件 < 50MB
- 查看文档列表：文件名、大小、上传时间、状态
- 删除文档：从知识库中移除文档
- 查看分块：展示文档切分后的 chunks

**知识库状态**：
- 活跃：正常使用中
- 索引中：文档正在处理
- 错误：索引失败需处理

**设计要点**：
- 知识库名称唯一性校验
- 嵌入模型选择影响后续检索效果
- 文档上传支持拖拽和点击选择
- 分块展示包含：文本内容、token 数、相似度（检索时）

#### 4.3.3 数据摄取

**批量上传功能**：
- 多文件选择（支持拖拽）
- 目标知识库选择
- 切分参数配置：
  - `chunk_size`：256-2048，默认 512
  - `overlap`：0-200，默认 50
- 实时进度展示
- 任务队列管理

**任务管理**：
- 任务列表：显示所有上传任务
- 任务状态：等待中、处理中、已完成、失败
- 任务详情：文件名、状态、进度百分比、错误信息
- 任务操作：重试失败任务、取消等待任务

**设计要点**：
- 大文件上传支持分片上传
- 任务状态通过轮询或 WebSocket 更新
- 失败任务保留错误日志便于排查
- 批量操作支持暂停/恢复

#### 4.3.4 意图管理

**意图树视图**：
- 树形结构展示意图层级关系
- 支持展开/折叠节点
- 节点显示：意图名称、触发关键词数量
- 拖拽调整意图层级（可选功能）

**意图列表管理**：
- 表格形式展示所有意图
- 字段：意图名称、父意图、关键词、响应策略、状态
- 新建意图：填写意图信息和配置
- 编辑意图：修改意图属性
- 删除意图：移除意图（需确认）

**意图配置项**：
- 意图名称：唯一标识
- 父意图：建立层级关系
- 触发关键词：用于意图识别
- 响应策略：直接回答/知识库检索/混合模式
- 优先级：多意图匹配时的选择依据

**设计要点**：
- 意图树最多支持 3 层深度
- 关键词支持正则表达式
- 响应策略影响 RAG 流程
- 意图启用/禁用状态控制

#### 4.3.5 链路追踪

**追踪列表**：
- 显示所有 RAG 调用记录
- 筛选条件：时间范围、状态、关键词搜索
- 字段：查询时间、查询文本、耗时、状态、用户
- 分页加载：支持翻页和每页条数设置

**追踪详情**：
- 查询信息：原始问题、查询时间、会话 ID
- 检索结果：
  - 匹配文档列表
  - 每个文档的相似度分数
  - 文档来源知识库
- 生成信息：
  - 使用的 LLM 模型
  - 完整 Prompt（包含上下文和检索文档）
  - 生成的回答内容
- 性能统计：
  - 意图识别耗时
  - 向量检索耗时
  - LLM 生成耗时
  - 总耗时

**设计要点**：
- 追踪数据由后端 AOP 拦截记录
- 详情页支持导出为 JSON
- 异常链路标红显示
- 可按耗时、相似度等维度排序

#### 4.3.6 系统设置

**LLM 配置**：
- 模型选择：下拉列表展示可用模型
- 温度参数：滑块调整 0.0-1.0
- 最大 Token 数：输入框设置
- API Key 配置（敏感信息加密存储）

**向量模型配置**：
- 嵌入模型选择
- 向量维度显示
- 批量处理大小

**检索参数**：
- Top K：返回文档数量（1-20）
- 相似度阈值：过滤低相关文档（0.0-1.0）
- 重排序开关：是否启用重排序模型

**提示词模板**：
- 系统 Prompt 编辑器（支持变量占位符）
- 回答格式要求配置
- 引用格式配置

**设计要点**：
- 配置修改后实时生效
- 敏感配置需管理员权限
- 配置变更记录日志
- 支持导入/导出配置文件

#### 4.3.7 用户管理

**用户 CRUD**：
- 用户列表：显示所有用户
- 新建用户：填写用户名、密码、角色
- 修改角色：user/admin 切换
- 删除用户：移除用户及关联数据

**用户字段**：
- 用户名：3-20 字符，唯一
- 密码：6-128 字符，哈希存储

### 4.4 权限控制设计

**角色定义**：
- `user`：普通用户，只能访问聊天功能
- `admin`：管理员，可访问所有功能

**路由守卫**：
- `RequireAuth`：验证用户登录状态
- `RequireAdmin`：验证管理员权限
- `RedirectIfAuth`：已登录用户重定向

**权限校验时机**：
- 路由级别：访问页面前校验
- 接口级别：调用 API 前携带 Token
- 操作级别：敏感操作前二次确认

### 4.5 数据流设计

**登录流程**：
1. 用户输入凭证 → 前端校验
2. POST `/api/ragent/user/login`
3. 后端返回 `{userId, token, role}`
4. 前端存储 Token 到 localStorage
5. 设置 Axios 请求头 `Authorization`
6. 根据角色跳转页面

**聊天流程**：
1. 用户输入消息 → chatStore.sendMessage()
2. 创建用户消息 + AI 占位消息
3. GET `/api/ragent/chat/stream?query=xxx&deepThinking=true`
4. EventSource 监听事件：
   - `meta` → 获取 conversationId、taskId
   - `thinking_delta` → 更新思考内容
   - `delta` → 更新回答内容
   - `completion` → 标记完成，附带引用来源
5. 更新消息状态和内容

**知识库管理流程**：
1. 创建知识库 → POST `/api/ragent/knowledge-base`
2. 上传文档 → POST `/api/ragent/knowledge-base/{id}/documents`
3. 后端切分文档 → 生成 embeddings → 存入向量库
4. 前端轮询任务状态 → 更新进度

### 4.6 异常处理设计

**网络异常**：
- 接口超时：显示重试按钮
- 401 未授权：跳转登录页
- 403 权限不足：提示无权限
- 500 服务错误：显示错误信息

**业务异常**：
- 文件上传失败：保留已上传文件，允许重试
- SSE 连接中断：显示"连接断开"，提供重新发送
- 会话不存在：提示并跳转到新会话

**用户操作异常**：
- 输入超长：显示字符计数和限制提示
- 重复提交：按钮禁用，显示 loading 状态
- 删除确认：弹出确认对话框
