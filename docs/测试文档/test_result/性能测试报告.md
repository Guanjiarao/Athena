## 二、测试方法

### 2.1 测试工具与环境

| 项目 | 说明 |
|------|------|
| 测试工具 | Apache JMeter 5.6.3 |
| 测试执行方式 | GUI 模式手动启动，所有线程组并发执行 |
| 目标服务器 | `http://192.168.227.251:13715/athena` |
| 认证方式 | Bearer Token（硬编码于 User Defined Variables） |
| 请求协议 | HTTP/1.1（HttpClient4 实现），Keep-Alive 启用 |
| 结果收集 | View Results Tree + Aggregate Report + Summary Report |

### 2.2 通用测试设计

**断言策略：** 所有接口均使用响应断言（Response Assertion），校验响应体中包含 `"code":200`（AI 模块为 `"code":"0"`），判定模式为字符串包含（Contains）。

**超时配置：** 连接超时统一 15s（AI/外部调用场景 30s），响应超时按场景分为 15s（常规读）、30s（常规写）、60s（长耗时查询/报告生成）。

**Think Time：** 各场景设置了 100ms~5s 不等的固定/随机定时器，模拟真实用户操作间隔，避免请求过于密集。

**线程组执行模式：** 所有 Thread Group 设置 `on_sample_error=continue`，单个请求失败不影响后续执行。`serialize_threadgroups=false`，所有场景同时并发启动。

**数据提取与传递：** 需要跨步骤传递数据的场景使用 JSON PostProcessor（JSONPath）提取响应字段存入变量，供后续 Sampler 引用。

## 四、总结与不足

### 4.1 总体结论

本次测试对 Athena 后端 **9 个模块 52 个接口** 进行了全面的性能评估。整体来看，系统在中等并发负载下表现良好：

**性能表现分层：**

| 层级 | 平均响应 | 代表模块 | 评价 |
|:---:|:---:|------|------|
| 优秀 | < 200ms | 用户、记录、经期 | 简单 CRUD，无外部依赖，代码质量高 |
| 良好 | 200~500ms | 博客、关系 | 含复杂查询/写操作，并发处理能力强 |
| 需优化 | 500ms~2s | 评论发布、RAG CRUD | 可能存在同步阻塞或低效 ORM 查询 |
| 重点关注 | > 10s | 健康报告（insight/report） | 需要架构层面重构 |

**核心优势：**
- 简单 CRUD 接口（用户/记录/经期）在 100ms 左右的延迟内完成，数据库交互高效
- 博客模块承载了最大的请求量（1,105 次 / 占总量的 35%），在高并发下仍保持了 84.8 req/s 的吞吐和稳定的响应
- 关系模块在高并发读场景（100 线程 × 3 循环）下，所有读接口无异常且 P99 控制在 1s 以内
- 所有被测接口在正确测试数据下均可正常返回（异常率实际为 0%），系统功能正确性得到验证

**待改进项：**

1. **健康报告接口（insight/report）— 最高优先级**
   - 平均 20.3s 的响应时间不可接受，且极度不稳定
   - 建议：引入异步生成 + 结果缓存机制；或拆分为多个子报告按需加载；考虑使用 Redis 缓存已生成的报告

2. **评论发布接口（comment/publish）— 高优先级**
   - 平均 1.4-1.8s 对于发布操作明显偏慢
   - 建议：排查同步阻塞点（内容审核？敏感词过滤？消息通知？），考虑异步化

3. **RAG 会话管理接口 — 中优先级**
   - conversations 列表和消息查询均超 1.5s，与简单 CRUD 预期不符
   - 建议：检查 N+1 查询问题；考虑为 conversations 列表添加分页索引

4. **博客浏览上报（blog/view）— 低优先级**
   - P95 延迟（1158ms）与平均值（429ms）差距大，存在偶发长尾
   - 建议：确认是否存在锁竞争或批量写入策略

### 4.2 测试方法局限性

本次性能测试在以下方面存在不足，后续可针对性地改进：

| 不足 | 影响 | 改进建议 |
|------|------|------|
| **单账号测试** — 所有请求使用同一 Token 和测试账号 | 无法评估多用户并发下的锁竞争、缓存命中率等真实场景表现 | 引入 CSV 数据文件驱动多账号参数化 |
| **固定测试数据** — blogId、recordId、cycleId 均为硬编码预设值 | 缓存效应可能掩盖真实性能；PUT/DELETE 同类 ID 并发冲突 | 动态提取上一请求返回的 ID，每个线程操作独立数据 |
| **无阶梯加压** — 所有线程组固定线程数，无递增负载场景 | 无法确定系统的吞吐拐点和最大并发容量 | 增加阶梯加压场景（如 10→50→100→200 线程逐步递增） |
| **Think Time 影响** — 部分场景的 Timer 降低了有效并发 | 吞吐量数据偏保守，不能反映系统的极限吞吐能力 | 增加无 Think Time 的极限压测场景 |
| **缺少稳定性/耐久测试** — 所有场景循环次数较少（1-5 次） | 无法发现内存泄漏、连接池耗尽、GC 停顿等长期运行问题 | 增加 30min-1h 的耐久测试，监控 JVM 内存和 GC |
| **无服务器资源监控** — 仅记录了客户端侧指标 | 无法关联响应时间与 CPU/内存/IO/数据库连接数等资源使用情况 | 配合 Prometheus/Grafana/JMX 采集服务端指标 |
| **AI 接口范围受限** — 排除了 chat、triage、external_ai 等外部依赖接口 | 无法评估后端代码中调用外部服务的封装层性能（如超时处理、重试逻辑、错误处理） | 新增专项测试，使用 Mock Server 模拟外部 AI 服务响应 |
| **缺少网络环境说明** — 未记录测试客户端与服务器之间的网络条件 | 网络延迟/带宽直接影响测试结果的可复现性 | 记录 ping/RTT、带宽、是否同网段等环境信息 |
| **结果数据未持久化** — 仅依赖 JMeter GUI 查看结果 | 历史测试无法回溯对比 | 配置 JMeter 将结果输出到 .jtl 文件，便于后续 Grafana/Jenkins 集成 |

### 4.3 建议后续行动

1. **短期（本迭代）：** 优先排查 insight/report 和 comment/publish 的性能瓶颈，进行针对性代码优化
2. **中期（下迭代）：** 引入多账号参数化测试、阶梯加压测试、增加服务端资源监控
3. **长期（持续优化）：** 建立定期性能回归测试机制，将 JMeter 脚本集成到 CI/CD 流水线中，每次发布前自动执行并比对历史基准
