# Athena 用户记忆中枢 + 知识图谱 设计方案

> 版本：v1.1（2026-07-26）图谱升级为 Neo4j 完整 GraphRAG（Local+Global）
> 状态：待评审
> 范围：athena-rag 后端、RAG 前端；预留 athena-record / athena-insight 接入

---

## 1. 目标与定位

### 1.1 两个能力

| 能力 | 定位 | 第一消费方 |
|------|------|-----------|
| **用户记忆中枢（Memory Hub）** | 平台级、跨会话的用户语义记忆 + 聚合画像 | RAG 智能问答 |
| **知识图谱（完整 GraphRAG）** | 知识库实体/关系图 + 社区摘要，支持局部检索增强与全局主题问答 | RAG 检索管线 |

### 1.2 关键设计立场

1. **记忆中枢是平台设施，不是 RAG 的私有功能**。RAG 对话抽取只是第一条数据源；
   月经记录系统（athena-record）、浏览行为（athena-insight 体系）后续通过预留通道接入。
2. **与 athena-insight 现有画像互补，不重复**：insight 的 `tb_user_feature_snapshot` /
   `tb_user_insight` 是算法/规则驱动的**结构化特征**（服务推荐引擎）；记忆中枢是
   **自然语言 + 向量**的语义记忆（服务 LLM 对话与个性化）。后期互相导入。
3. **记忆不引入新中间件**：存 PostgreSQL（pgvector），复用现有 Redis / RocketMQ /
   多模型 LLM 网关。**图谱采用 Neo4j 5.x + GDS**（Docker 单容器）：完整 GraphRAG
   所需的 Leiden 社区检测、全局问答、深遍历是其原生能力，且自带向量索引。
4. **包边界独立**：记忆中枢代码放独立包 `usermemory`，表独立，将来可无痛拆微服务。

## 3. 模块一：用户记忆中枢

### 3.1 数据模型

```sql
-- 原子事实记忆（带向量，支持语义检索）
CREATE TABLE t_user_memory (
    id               VARCHAR(20)  NOT NULL PRIMARY KEY,
    user_id          VARCHAR(20)  NOT NULL,
    memory_type      VARCHAR(16)  NOT NULL,  -- profile/fact/preference/episode
    content          TEXT         NOT NULL,  -- 自然语言事实,如"痛经严重,经期第1-2天明显"
    embedding        vector(1536),
    source_system    VARCHAR(16)  NOT NULL DEFAULT 'rag_chat',
                                             -- rag_chat/record/behavior/manual
    source_ref       VARCHAR(64),            -- 来源引用:conversationId/recordId等
    confidence       REAL         NOT NULL DEFAULT 0.8,   -- 置信度 0~1
    importance       REAL         NOT NULL DEFAULT 0.5,   -- 重要度 0~1
    valid_until      TIMESTAMP,              -- 时效性记忆过期时间,NULL=永久
    access_count     INTEGER      NOT NULL DEFAULT 0,
    last_accessed_at TIMESTAMP,
    enabled          SMALLINT     NOT NULL DEFAULT 1,
    create_time      TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time      TIMESTAMP    NOT NULL DEFAULT CURRENT_TIMESTAMP,
    deleted          SMALLINT     NOT NULL DEFAULT 0
);
CREATE INDEX idx_um_user ON t_user_memory (user_id, enabled, deleted);
CREATE INDEX idx_um_embedding ON t_user_memory USING hnsw (embedding vector_cosine_ops);

-- 聚合画像（每用户一行,LLM 定期归纳）
CREATE TABLE t_user_profile (
    id               VARCHAR(20) NOT NULL PRIMARY KEY,
    user_id          VARCHAR(20) NOT NULL,
    base_json        JSONB,      -- 基础:年龄段/身高体重等
    health_json      JSONB,      -- 健康:周期特征/症状/健康关注点
    preference_json  JSONB,      -- 偏好:内容偏好/沟通风格
    summary          TEXT,       -- 一段话画像(直接可注入 prompt)
    memory_count     INTEGER     NOT NULL DEFAULT 0,
    version          INTEGER     NOT NULL DEFAULT 1,
    last_built_at    TIMESTAMP,
    create_time      TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    update_time      TIMESTAMP   NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uk_profile_user UNIQUE (user_id)
);
```

### 3.2 核心服务（包 `com.nageoffer.ai.ragent.usermemory`）

```
usermemory/
├── controller/  UserMemoryController      /memory CRUD+搜索(用户端/管理端)
│                UserProfileController     /profile 查询、触发重建
│                MemoryIngestController    /internal/memory/ingest (内部,预留②)
├── service/     MemoryIngestService       统一写入口:抽取候选→合并判定→落库
│                MemoryRetrieveService     向量检索 topK + 阈值 + 时效过滤
│                MemoryExtractService      LLM 从对话轮次抽取候选事实
│                ProfileBuildService       LLM 归纳记忆→画像(定时+阈值触发)
├── mq/          MemoryExtractProducer/Consumer   对话后异步抽取(通道①)
│                MemoryEventConsumer              memory-event 主题(通道③,预留)
├── dao/         UserMemoryMapper, UserProfileMapper
└── config/      LongTermMemoryProperties  rag.memory.long-term.*
```

**合并判定（mem0 风格）**：新候选事实 → 向量召回该用户 top5 相似记忆 →
LLM 判定 `ADD`（新事实）/ `UPDATE`（覆盖旧值，如体重变化）/ `DELETE`（旧事实失效）/
`NOOP`（重复）。判定模型与抽取模型均默认 `deepseek-v4-flash`。

**检索注入**：在 `StreamChatPipeline.loadMemory` 后并行执行
`MemoryRetrieveService.search(userId, rewrittenQuestion, topK=5, minScore=0.5)`，
过滤 `valid_until` 过期项；命中作为「用户长期记忆」段拼入 system prompt
（模板新增 `answer-chat-kb.st` 的 `{longTermMemory}` 占位），并写入
`StreamChatContext.memoryHits` 随 finish 事件下发。命中后异步更新
`access_count` / `last_accessed_at`。

**画像构建**：定时任务（每日）+ 记忆增量阈值触发（新增≥10 条），
LLM 输入该用户全部有效记忆 + 现有画像 → 输出四段 JSON + summary，版本 +1。

## 4. 模块二：知识图谱（完整 GraphRAG）

### 4.1 存储选型与图模型

采用 **Neo4j 5.x Community + GDS 插件**，Docker 单容器部署（与 PG/Redis 同机）。
选型理由见 §9；要点：Leiden 社区检测 / 全局问答 / 变长遍历为原生能力，
Neo4j 5 自带向量索引（实体归一化与查询实体匹配不出库）；Community 版单库，
多知识库用 `kbId` 属性隔离；**chunk 正文仍在 PG**，图中只放轻量 Chunk 节点做溯源锚点。

```yaml
# application-dev.yaml 新增
neo4j:
  uri: bolt://121.41.200.73:7687
  username: neo4j
  password: <见环境配置>
```

图模型：

```cypher
(:Entity {id, kbId, name, type, description, aliases, embedding, mentionCount})
(:Chunk  {id, kbId, docId})                      // 轻节点,正文在 PG t_knowledge_chunk
(:Community {id, kbId, level, title, summary, entityCount, dirty})

(:Entity)-[:REL {type, description, weight}]->(:Entity)
(:Entity)-[:MENTIONED_IN]->(:Chunk)
(:Entity)-[:IN_COMMUNITY]->(:Community)

CREATE CONSTRAINT entity_id IF NOT EXISTS FOR (e:Entity) REQUIRE e.id IS UNIQUE;
CREATE INDEX entity_kb_name IF NOT EXISTS FOR (e:Entity) ON (e.kbId, e.name);
CREATE VECTOR INDEX entity_embedding IF NOT EXISTS FOR (e:Entity) ON e.embedding
  OPTIONS {indexConfig: {`vector.dimensions`: 1536,
                         `vector.similarity_function`: 'cosine'}};

Java 访问层：官方 `neo4j-java-driver` 直写 Cypher（语句可控、便于调优），
所有图操作收敛在 `GraphStore` 接口后面（便于单测 mock 与将来替换）。

### 4.2 图谱构建（摄取侧，包 `com.nageoffer.ai.ragent.kg`）

1. **新增摄取节点类型 `GRAPH_EXTRACTOR`**（`IngestionNodeType` 加枚举 +
   `GraphExtractorNode`，挂在 INDEXER 之后，pipeline 可选配置）。
2. 每个 chunk 走 LLM 抽取提示词（新增 `graph-extract.st` 模板，输出 JSON：
   entities[{name,type,description}] + relations[{source,target,type,description}]），
   针对女性健康领域在提示词中给定实体类型清单。
3. **实体归一化**：同 kb 内先精确名/别名匹配 → 未命中走 Neo4j 向量索引相似匹配
   （阈值 0.92）合并为已有实体（追加别名、合并描述、mentionCount+1），否则 MERGE 新建。
4. **社区构建（GraphRAG 核心步骤）**：回填完成或增量实体累积超阈值后触发
   `CommunityBuildJob`：
   - GDS Leiden 对该 kbId 子图跑社区检测（第一期只做单层 level 0，字段留分层余地）
   - 每个社区收集成员实体、关系描述、高权重关联 chunk → LLM 生成社区标题+摘要
     （新模板 `community-summarize.st`，模型 deepseek-v4-pro）→ 写回 Community 节点
5. **回填**：`POST /kg/admin/backfill/{kbId}` 对已有文档批量补抽取，
   复用 `t_ingestion_task` 跟踪进度，RocketMQ 异步逐文档执行，完成后自动触发社区构建。
6. 文档删除/重新摄取时清理其 MENTIONED_IN 边；孤儿实体标记删除；
   涉及社区置 `dirty=true` 等待重建。

### 4.3 检索融合：Local + Global 双模式（GraphRAG）

**Local Search**——具体问题，作为 `RetrievalEngine` 第三通道（与 vector-global /
intent-directed 并行）：

```
改写后 query → 抽取查询实体(复用 t_query_term_mapping 归一化)
→ Neo4j 匹配实体(精确+别名+向量索引)
→ Cypher 扩展 1~2 跳邻居,按 weight/mentionCount 排序截断
→ 收集: ①MENTIONED_IN 关联 chunk(回 PG 取正文,进统一 rerank 池)
        ②关系三元组文本("痛经 --可缓解于--> 热敷:...")
→ 三元组作为「知识图谱上下文」独立段注入 prompt
```

**Global Search**——全局/主题性问题（"这个知识库整体讲了什么""经期饮食有哪些方面"），
map-reduce 社区摘要：

```
路由判定: 意图解析阶段扩展——查询实体命中弱 且 问题呈全局性特征时走 global
→ Map: 取该 kb 全部社区摘要,embedding 粗排 topN,LLM 逐个评相关性打分
→ Reduce: 高分社区摘要合成「全局上下文」→ 生成回答,引用指向社区(可跳图谱页)
```

配置 `rag.search.channels.graph`: enabled / mode(auto|local|global) / max-hops(1) /
max-entities / max-triples / global-top-communities。全链路打 trace 节点。

## 7. 拓展路线（平台搭好后）

1. **接入 athena-record（月经系统）**：新建 `RecordMemorySyncJob`，
   定期调用 record 已有内部 API（`/athena/record/internal/insight/cycle-stats`、
   `/prediction`），把周期统计转成**时效性记忆**写入通道②：
   如「当前处于黄体期,预计 X 日来潮」（valid_until=预测日）、「平均周期 31 天,偏长」。
2. **接入浏览行为**：App 端行为事件（浏览/点赞/收藏主题）经 RocketMQ
   `memory-event` 进通道③，按 Topic 聚合成 preference 记忆
   （与 athena-insight 的 tb_user_insight 内容偏好互为印证,可直接导入其结论）。
3. **画像反哺**：`/profile` API 输出供 insight 推荐引擎作为语义特征补充。
4. **图谱升级**：多层社区(level>0)分层摘要、跨知识库实体对齐、图谱质量评测集
   （社区检测与全局问答已纳入主线范围)。

| 图存储 | Neo4j 5.x + GDS(替代 v1.0 的 PG 方案) | 目标升级为完整 GraphRAG:Leiden 社区检测/全局问答/变长遍历是原生能力;自带向量索引与 Browser 可视化;代价是多一个 Docker 容器 |
| 图访问层 | 官方 java-driver + GraphStore 接口 | Cypher 语句可控;接口隔离便于单测与替换;chunk 正文留 PG,图中只放溯源锚点 |
| 记忆中枢落点 | athena-rag 内独立包 | pgvector+LLM 网关都在;包边界+独立表保留拆分退路 |
| 抽取/判定模型 | deepseek-v4-flash | 成本低,结构化输出够用;画像归纳用 deepseek-v4-pro |
| 前端图库 | react-force-graph-2d | canvas 性能好,API 简单,包体小 |
| 记忆隔离粒度 | user 级全局(不分 KB) | 用户记忆天然跨知识库;图谱按 kb_id 隔离 |
| 抽取时机 | 每轮对话后异步(MQ) | 不阻塞 SSE;失败可重试;幂等由合并判定兜底 |
