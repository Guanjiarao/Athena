# 搜索 v1 版本方案

> 模块：`athena-ground-biz`
> 目标：在当前仅使用 MySQL、不引入 ES 的前提下，先落地一版简单、稳定、可上线的笔记搜索能力。
> 定位：**搜索 v1 只解决“先能搜、先够用”**，不追求复杂相关性排序、中文分词、高亮和搜索推荐。

## 一、方案结论

搜索 v1 不采用全文检索，不引入 ES，也不直接对大文本正文做全量 `%LIKE%` 搜索。

第一版采用下面的原则：

1. 以 `tb_note_basic` 作为主查询入口
2. 优先搜索标题 `title`
3. 公开搜索只搜索“审核通过”的内容
4. 我的搜索只搜索“当前用户自己的内容`
5. 正文 `tb_note_content.content` **第一版默认不参与搜索**
6. 排序先按：`is_top`（如后续接入）/ `update_time desc` / `note_id desc`
7. 搜索结果返回轻量列表，不在搜索 SQL 中做重查询拼装

这样做的原因很直接：

- 当前标题位于 `tb_note_basic`，适合作为搜索入口
- 正文在 `tb_note_content`，且为大字段，直接 `LIKE '%keyword%'` 成本高
- 第一版先把“可用搜索”做出来，后续如果体验不足，再平滑升级到 `MySQL FullText` 或 `ES`

---

## 二、第一版要解决的问题

当前 `athena-ground` 已经具备：

- 公开列表
- 按频道列表
- 按类型列表
- 我的文章列表
- 公开详情
- 审核状态控制

但还缺少统一的“关键词搜索”能力。

搜索 v1 的目标是：

1. 用户可以按关键词搜索公开可见笔记
2. 用户可以在“我的文章”范围内按关键词搜索自己的内容
3. 搜索逻辑与现有审核规则一致
4. SQL 能尽量复用当前 `tb_note_basic` 结构
5. 不引入复杂中间表，不引入异步索引构建流程

---

## 三、搜索范围定义

## 3.1 搜索对象

第一版只搜索笔记基础信息表中的标题字段：

- 表：`tb_note_basic`
- 字段：`title`

第一版暂不搜索：

- `tb_note_content.content`
- 标签扩展字段
- 作者昵称
- topic 名称
- channel 名称

说明：

标题搜索是最稳的第一步，命中率虽然不如全文搜索，但性能和实现复杂度最可控。

## 3.2 搜索场景

建议拆成两个独立场景：

### 场景 A：公开搜索

面向普通用户，用于搜索可公开展示的内容。

过滤规则：

- 只查 `status = 1`
- 可选按 `type` 过滤
- 可选按 `channel_id` 过滤
- 关键词匹配 `title`

### 场景 B：我的文章搜索

面向作者本人，用于搜索自己发过的文章。

过滤规则：

- `user_id = 当前用户`
- 不限制 `status = 1`
- 可选按状态过滤，如待审核/已通过/已拒绝
- 可选按 `type` 过滤
- 关键词匹配 `title`

---

## 四、为什么第一版不直接搜正文

不建议第一版直接对 `tb_note_content.content` 使用：

```sql
content like '%关键词%'
```

原因：

1. `content` 是大文本字段，扫描成本高
2. 前置 `%` 基本无法有效利用普通索引
3. 标题搜索已经能覆盖第一版大部分用户预期
4. 当前系统更需要“稳定上线”，不是“复杂搜索体验”
5. 一旦笔记量上来，正文模糊搜索很容易成为慢 SQL

因此 v1 采取保守策略：

- **只搜标题**
- 如果后续确认用户强依赖正文搜索，再升级到 v2

---

## 五、查询规则设计

## 5.1 关键词处理规则

建议服务层做以下基础处理：

1. 去掉首尾空格：`trim`
2. 空关键词不执行搜索，直接返回参数错误或空结果
3. 关键词长度建议限制为 `1 ~ 30`
4. 模糊匹配时统一使用：

```sql
like concat('%', #{keyword}, '%')
```

说明：

- 第一版不做分词
- 不做多关键词布尔搜索
- 不做拼音搜索
- 不做同义词搜索

## 5.2 排序规则

第一版排序保持简单稳定：

### 公开搜索排序

优先建议：

1. 更新时间倒序 `update_time desc`
2. `note_id desc` 作为稳定次序

如果后续希望与现有列表一致，也可以补充置顶优先级，但第一版不强依赖。

### 我的文章搜索排序

同样按：

1. `update_time desc`
2. `note_id desc`

说明：

第一版不做相关性得分排序，因为目前只是标题模糊查询，做复杂打分收益不高。

## 5.3 分页规则

保持与当前列表接口一致：

- `pageNum`
- `pageSize`
- `offset = (pageNum - 1) * pageSize`

建议默认值：

- `pageNum = 1`
- `pageSize = 10`
- 最大 `pageSize = 20` 或 `50`

---

## 六、数据库与索引建议

## 6.1 第一版是否需要新增字段

**不需要新增字段。**

现有 `tb_note_basic` 已经足够支撑标题搜索：

- `note_id`
- `user_id`
- `title`
- `type`
- `status`
- `channel_id`
- `update_time`

## 6.2 索引建议

由于 `title like '%关键词%'` 不能很好利用普通索引，所以索引重点不是给 `title` 建单列索引，而是优先保障过滤条件和排序字段。

建议增加或确认以下索引：

### 公开搜索索引

```sql
CREATE INDEX idx_note_basic_status_type_channel_update
ON tb_note_basic (`status`, `type`, `channel_id`, `update_time`);
```

### 我的文章搜索索引

```sql
CREATE INDEX idx_note_basic_user_status_type_update
ON tb_note_basic (`user_id`, `status`, `type`, `update_time`);
```

如果希望减少索引数量，也可以按实际查询主路径做折中，例如拆成：

```sql
CREATE INDEX idx_note_basic_status_update
ON tb_note_basic (`status`, `update_time`);

CREATE INDEX idx_note_basic_user_update
ON tb_note_basic (`user_id`, `update_time`);
```

说明：

- 第一版索引主要帮助先缩小候选集
- 真正的标题模糊匹配仍然需要在候选结果中做扫描
- 但比直接全表扫要稳得多

---

## 七、接口设计建议

第一版建议不要做一个过于泛化的大搜索接口，而是按当前业务拆两个接口。

## 7.1 公开搜索接口

### 接口语义

按关键词搜索公开可见笔记。

### 请求参数建议

```json
{
  "keyword": "经期",
  "type": 1,
  "channelId": 3,
  "pageNum": 1,
  "pageSize": 10
}
```

字段说明：

- `keyword`：必填，搜索关键词
- `type`：可选，按笔记类型过滤
- `channelId`：可选，按频道过滤
- `pageNum`：页码
- `pageSize`：分页大小

### 返回结果建议

直接复用现有列表返回结构风格，至少包括：

- `blogId`
- `title`
- `coverUrl`
- `type`
- `channelId`
- `channelName`
- `userDTO`
- `likeTotal`
- `createTime`
- `updateTime`

不建议在第一版返回：

- 命中片段
- 高亮字段
- 相关性分数

## 7.2 我的文章搜索接口

### 接口语义

搜索当前用户自己的文章。

### 请求参数建议

```json
{
  "keyword": "备孕",
  "status": 0,
  "type": 1,
  "pageNum": 1,
  "pageSize": 10
}
```

字段说明：

- `keyword`：必填
- `status`：可选，便于筛待审核/已通过/已拒绝
- `type`：可选
- `pageNum` / `pageSize`：分页参数

### 返回结果建议

在复用 `BlogListDTO` 的基础上，保留：

- `status`
- `reviewRemark`

因为“我的文章”需要显示审核状态。

## 八、Mapper 查询建议

第一版建议新增专门的搜索查询，不要把现有列表 SQL 改得过于复杂。

## 8.1 公开搜索 SQL 示例

```sql
SELECT
    note_id, user_id, title, cover_url, `type`, `status`,
    review_remark, review_time, reviewer_id,
    channel_id, channel_name, create_time, update_time
FROM tb_note_basic
WHERE `status` = 1
  AND title LIKE CONCAT('%', #{keyword}, '%')
  <if test="type != null">
    AND `type` = #{type}
  </if>
  <if test="channelId != null">
    AND channel_id = #{channelId}
  </if>
ORDER BY update_time DESC, note_id DESC
LIMIT #{offset}, #{pageSize}
```

## 8.2 我的文章搜索 SQL 示例

```sql
SELECT
    note_id, user_id, title, cover_url, `type`, `status`,
    review_remark, review_time, reviewer_id,
    channel_id, channel_name, create_time, update_time
FROM tb_note_basic
WHERE user_id = #{userId}
  AND title LIKE CONCAT('%', #{keyword}, '%')
  <if test="status != null">
    AND `status` = #{status}
  </if>
  <if test="type != null">
    AND `type` = #{type}
  </if>
ORDER BY update_time DESC, note_id DESC
LIMIT #{offset}, #{pageSize}
```

说明：

- 公开搜索和我的搜索建议分开写 SQL
- 这样语义更清晰，后面升级也容易分别演进

## 九、服务层实现建议

## 9.1 建议新增能力边界

建议在 `GroundService` 上增加两个方法：

1. `searchPublicNotes(...)`
2. `searchMyNotes(...)`

或者命名为：

1. `searchBlogList(...)`
2. `searchMyBlogList(...)`

重点不是名字，而是要把公开搜索和我的搜索分开。

## 9.2 服务层处理步骤

每个搜索接口建议统一走以下步骤：

1. 校验分页参数
2. 校验关键词是否为空
3. 对关键词做 `trim`
4. 调用 `NoteBasicDOMapper` 搜索基础列表
5. 复用 `basicToBlogDTO(...)` 转换为列表 DTO
6. 返回结果

## 9.3 第一版不要做的事

服务层第一版不建议加入：

- 关键词纠错
- 搜索历史
- 热搜词
- 多字段权重打分
- 混合正文召回
- 搜索埋点聚合

这些都可以放到后续版本。

## 十、用户体验建议

虽然 v1 很简单，但为了体验不要太差，建议前端配合以下规则：

1. 搜索框提示语明确写成“搜索标题”
2. 空关键词不发请求
3. 无结果时提示：未找到相关标题，可尝试更换关键词
4. “我的文章搜索”页可加状态筛选
5. 搜索结果页先不展示高亮，避免前后端复杂度上升

这样用户对第一版能力边界会更清楚，不会误以为系统支持全文搜索。

---

## 十一、已知局限

搜索 v1 的局限需要明确接受：

1. 只能搜标题，不能搜正文
2. 中文搜索能力弱，没有分词
3. `LIKE '%keyword%'` 在数据量大时性能一般
4. 没有相关性排序，命中结果按更新时间为主
5. 没有高亮、联想、纠错、同义词

这不是缺陷，而是第一版刻意控制范围后的结果。

---

## 十二、升级路线建议

当搜索 v1 上线后，如果出现以下信号，就应考虑升级：

1. 用户经常反馈“标题搜不到正文内容”
2. 搜索请求响应时间明显上升
3. 数据量增长后慢 SQL 增多
4. 需要支持更自然的中文搜索
5. 需要做高亮、相关性、热搜和推荐

建议升级路线如下：

### v2

在 MySQL 内部升级：

- 引入全文索引能力
- 让 `title + content` 进入统一搜索
- 视 MySQL 版本评估中文 FullText 能力

### v3

引入专业搜索引擎：

- Elasticsearch / OpenSearch
- 支持分词、相关性、高亮、联想词
- 支持搜索索引异步更新

---

## 十三、最终建议

对于当前 `athena-ground`，搜索 v1 的最佳落地方式是：

1. **只搜索 `tb_note_basic.title`**
2. **公开搜索只查 `status = 1`**
3. **我的搜索按 `user_id` 查询，不限制通过状态**
4. **支持 `type`、`channelId`、`status` 等结构化过滤**
5. **统一按 `update_time desc, note_id desc` 排序**
6. **正文搜索暂不做**

这是当前成本最低、风险最小、最容易快速上线的一版方案。

后续如果你要继续推进，我建议下一步直接做两件事：

1. 补这份方案对应的接口定义与 DTO
2. 补 `NoteBasicDOMapper` 的搜索 SQL 与服务实现

这样就可以把搜索 v1 真正落地到代码里。
