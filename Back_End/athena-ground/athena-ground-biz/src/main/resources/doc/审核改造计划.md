# 审核改造计划

> 范围：仅做第一版必做项，不引入额外增强能力。
> 模块：`athena-ground-biz`
> 目标：为文章/笔记增加审核流，确保只有审核通过的内容对外展示，并且只有审核通过的知识类文章才进入 RAG。

## 一、第一版目标

本次只落地以下必做能力：

1. 将审核状态从详情表迁移到基础表 `tb_note_basic`
2. 用户提交文章后默认进入“待审核”状态
3. 公开列表、公开详情只展示“审核通过”的文章
4. “我的文章”列表保留全部状态，并返回审核状态
5. 增加后台审核接口：待审核列表、审核详情、审核通过、审核拒绝
6. 审核通过后，知识类文章调用 `upload` 接口同步到 RAG

本次明确 **不做**：

- 不删除数据库中旧的 `tb_note.status` 字段
- 不接入旧 MQ 实验链路
- 不增加知识库同步状态字段
- 不做审核历史分页列表
- 不做重新提交审核/编辑后二审
- 不做草稿能力

---

## 二、现状问题

当前 `athena-ground` 中：

- 列表主要查询 `tb_note_basic`
- 详情主要查询 `tb_note`
- 审核状态当前放在 `tb_note.status`
- `submitNote()` 在发布成功后，会对知识类文章直接调用 `athenaNoteDocumentUploadService.upload(...)`

这会带来几个问题：

1. `tb_note_basic` 没有 `status`，公开列表无法天然过滤“只显示审核通过”
2. 详情状态和列表状态不在同一层，导致展示规则难统一
3. 知识类文章在未审核时就可能进入 RAG
4. 后台审核能力缺少统一入口

因此第一版要把“审核状态”提升为基础记录字段，并把知识同步时机调整为“审核通过后”。

---

## 三、第一版业务规则

### 3.1 审核状态定义

建议固定为：

- `0`：待审核
- `1`：审核通过
- `2`：审核拒绝

### 3.2 提交规则

用户调用提交接口后：

- 写入 `tb_note_basic`
- 写入 `tb_note`
- 写入 `tb_note_content`
- 写入 `tb_note_count`
- 其中 `tb_note_basic.status = 0`
- 不调用 RAG upload 接口

### 3.3 展示规则

#### 公开列表
仅显示 `status = 1` 的文章。

包括：

- 广场列表
- 按频道列表
- 按类型列表

#### 公开详情
普通用户只能查看 `status = 1` 的文章。

#### 我的文章
作者自己的文章列表保留全部状态，不过滤。
前端通过返回的 `status` 展示“待审核 / 已通过 / 已拒绝”。

### 3.4 审核规则

#### 审核通过
- 将 `tb_note_basic.status` 改为 `1`
- 记录审核时间、审核人
- 如果文章类型属于知识类（`type != 0 && type != 1 && type != 2`），调用 `upload` 接口同步到 RAG

#### 审核拒绝
- 将 `tb_note_basic.status` 改为 `2`
- 记录审核时间、审核人、拒绝原因
- 不调用 `upload`

## 四、数据结构改造

## 4.1 `tb_note_basic` 新增字段

建议执行：

```sql
ALTER TABLE tb_note_basic
ADD COLUMN status TINYINT NOT NULL DEFAULT 0 COMMENT '审核状态：0待审核 1审核通过 2审核拒绝',
ADD COLUMN review_remark VARCHAR(255) NULL COMMENT '审核备注/拒绝原因',
ADD COLUMN review_time DATETIME NULL COMMENT '审核时间',
ADD COLUMN reviewer_id BIGINT NULL COMMENT '审核人ID';
```

## 4.2 `tb_note.status`

第一版不删库字段，但代码中不再以 `tb_note.status` 作为审核真源。

审核状态真源统一改为：

- `tb_note_basic.status`

## 5.4 Service 层

### `NotePublishServiceImpl`
改造点：

- 发布时将 `NoteBasicDO.status` 设置为 `0`
- 不再写 `NoteDO.status = 1`

### `GroundServiceImpl.submitNote()`
改造点：

- 保留原有参数校验
- 保留调用 `notePublishService.publish(noteSubmitDTO)`
- 删除提交成功后立即调用 `athenaNoteDocumentUploadService.upload(...)` 的逻辑
- 返回语义调整为“提交成功，等待审核”

### 新增 `NoteReviewService`
建议新增审核服务，职责包括：

- 获取待审核列表
- 获取审核详情
- 审核通过
- 审核拒绝

### 新增 `NoteReviewServiceImpl`
核心职责：

#### `approve(noteId, reviewerId)`
1. 校验文章存在
2. 校验状态必须为待审核
3. 更新为审核通过
4. 记录 `reviewTime`、`reviewerId`
5. 查询文章标题、内容、类型、作者信息
6. 如果属于知识类，则调用 `athenaNoteDocumentUploadService.upload(...)`

#### `reject(noteId, reviewerId, reviewRemark)`
1. 校验文章存在
2. 校验状态必须为待审核
3. 更新为审核拒绝
4. 写入 `reviewRemark`、`reviewTime`、`reviewerId`
5. 不调用 upload

### 事务建议

审核通过时：

- 数据库状态更新放在本地事务内
- `upload(...)` 放在事务提交后执行

原因：

- `upload` 是外部 HTTP 调用，不应放入数据库事务
- 避免审核事务时间过长
- 避免远程调用失败影响审核主流程

## 5.5 Controller 层

### 前台接口
保留现有前台入口：

- `POST /athena/blog/submit`
- `GET /athena/blog/list`
- `GET /athena/blog/listBychannelId`
- `GET /athena/blog/listByTypeId`
- `GET /athena/blog/myList`
- `GET /athena/blog/Detail`

#### 改造要求
- `submit`：只提交审核，不触发 RAG 上传
- 公开列表：只展示审核通过
- `myList`：返回全部状态
- `Detail`：公开访问时只允许查看审核通过文章

### 后台审核接口
建议新增控制器：`AdminNoteReviewController`

建议接口如下：

#### 1. 获取待审核列表
`GET /athena/admin/blog/review/pending`

参数：
- `pageNum`
- `pageSize`
- `type`（可选）
- `channelId`（可选）

#### 2. 获取审核详情
`GET /athena/admin/blog/review/detail?noteId=xxx`

#### 3. 审核通过
`POST /athena/admin/blog/review/approve`

请求体：

```json
{
  "noteId": 123
}
```

#### 4. 审核拒绝
`POST /athena/admin/blog/review/reject`

请求体：

```json
{
  "noteId": 123,
  "reviewRemark": "内容不符合发布规范"
}
```

## 六、查询逻辑调整

## 6.1 公开列表
以下查询必须加 `status = 1`：

- `getBlogListPage()` 对应查询
- `getBlogListByChannelId()` 对应查询
- `getBlogListByType()` 对应查询

## 6.2 我的列表
`getBlogListByUserId()` 保持不加状态限制。

## 6.3 详情查询
建议调整为：

1. 先查 `tb_note_basic`
2. 判断是否存在
3. 判断当前文章是否为审核通过
4. 若不是审核通过，则不允许公开访问
5. 再查 `tb_note`、`tb_note_content`、`tb_note_count`

第一版若不做“作者本人可查看未通过详情”的扩展，则可以先按最简单规则落地：

- 仅 `status = 1` 可查详情

这样实现最小、风险最低。

## 八、第一版验收标准

完成后应满足以下标准：

- [ ] 用户提交文章后状态为待审核
- [ ] 新提交文章不会立即进入 RAG
- [ ] 公开列表只能看到审核通过文章
- [ ] 公开详情只能看到审核通过文章
- [ ] “我的文章”可看到自己的待审核/已通过/已拒绝状态
- [ ] 管理员可以获取待审核列表
- [ ] 管理员可以查看待审核详情
- [ ] 管理员可以审核通过文章
- [ ] 管理员可以审核拒绝文章并填写原因
- [ ] 审核通过后，知识类文章会调用 `upload` 接口同步到 RAG
- [ ] 审核拒绝后，不会调用 `upload`

## 十、最终结论

第一版采取“最小闭环”策略：

- 审核状态真源切到 `tb_note_basic`
- 提交只入库，不入知识库
- 公开内容只展示审核通过
- 审核通过后才调用 `upload`

这样可以最小成本完成审核能力闭环，并保证 RAG 中只进入审核通过的知识类文章。
