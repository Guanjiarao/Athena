# 05-模块职责图

## 1. 总览

这份文档按**类**来列分诊台各模块的职责、输入、输出和禁区。

它的目标不是追求抽象完美，而是让每个类的边界足够清楚，方便：
- 阅读代码
- 排查问题
- 做后续重构
- 避免把旧计划误写成现状

---

## 2. 总体模块分层

### 已确认

当前代码可以稳定分成这些层：

1. 接入层
2. 编排层
3. turn understanding 链
4. 结构化抽取链
5. 状态归约链
6. 规划 / 校验链
7. 风险链
8. 回复层
9. 核心模型层

---

## 3. 接入层

### 3.1 `TriageController`

**职责**
- 暴露 triage 主入口
- 暴露文本补全代理入口
- 暴露视觉分析代理入口
- 兜底异常，保证前端固定返回结构

**输入**
- `TriageAnalyzeRequest`
- `ClientChatCompletionRequest`
- `VisionAnalyzeRequest`

**输出**
- `TriageAnalyzeResponse`
- `ClientChatCompletionResponse`
- `VisionAnalyzeResponse`

**不能做什么**
- 不能决定 triage 策略
- 不能直接改 session state
- 不能自己做结构化理解或风险判断

**依赖谁**
- `TriageOrchestratorService`
- `TriageAiProxyService`

**已确认**
- 这是 triage 对外最外层入口

---

### 3.2 Request / VO 类

**职责**
- 承载 API 请求与响应字段
- 提供对外协议结构

**不能做什么**
- 不承载业务推理
- 不做状态归约
- 不做 planner 或 risk 决策

**已确认**
- 这些类只是协议容器

---

## 4. 编排层

### 4.1 `TriageOrchestratorServiceImpl`

**职责**
- 创建或恢复 `TriageContext`
- 重置当前轮状态
- 追加用户输入到会话历史
- 控制会话记忆压缩
- 调用状态机推进主流程
- 保存 context 与终态 context

**输入**
- `TriageAnalyzeRequest`
- `TriageSessionManager`
- `TriageRepository`
- `TriageModelGateway`
- `TriageSessionProperties`
- `TriageConversationMemoryHelper`

**输出**
- `TriageAnalyzeResponse`

**不能做什么**
- 不能直接做 question gap 策略
- 不能直接做主诉修正
- 不能替代 state machine

**依赖谁**
- `TriageStateMachine`
- `TriageSessionManager`
- `TriageRepository`
- `TriageModelGateway`

**已确认**
- 这是会话编排中心

---

### 4.2 `TriageStateMachine`

**职责**
- 定义状态流转表
- 驱动 parsing / validation / risk / report
- 处理异常降级
- 决定终态与中断态

**输入**
- `TriageContext`
- 各阶段 worker

**输出**
- `TriageState`
- `nextAction`
- `finalReply`

**不能做什么**
- 不能替代具体 worker 的解析逻辑
- 不能直接写业务抽取结果
- 不能自己生成问诊内容

**依赖谁**
- `TriageStageExecutor`
- `RiskStratifierWorker`
- `TriageReplyBuilder`

**已确认**
- 它是阶段调度器，不是业务解析器

---

### 4.3 `TriageStageExecutor`

**职责**
- 串起 parsing 阶段
- 串起 validation 阶段
- 把 planner 输出同步成 missing fields / clarification

**输入**
- `TriageContext`
- parsing / validation 阶段 worker

**输出**
- parsing / validation 的阶段性描述

**不能做什么**
- 不能自己发明业务规则
- 不能绕过 state machine

**已确认**
- 它是阶段执行器，不是策略器

---

### 4.4 `TriageReplyBuilder`

**职责**
- 生成澄清回复
- 生成风险警示回复
- 生成分诊报告

**输入**
- `TriageContext`
- `TriageModelGateway`

**输出**
- 对外可见回复文本

**不能做什么**
- 不能重新计算分诊状态
- 不能修改 session truth

**已确认**
- 它只负责把结果说出来

## 12. 最容易混淆的职责对照

| 模块 | 应做 | 不应做 |
|---|---|---|
| `TurnUnderstandingWorker` | 接 turn understanding 执行链 | 写 session truth |
| `TurnComplaintSemanticsCoordinator` | 补主诉、answered slot、correction、risk signal | 直接替代 reducer |
| `StateReducer` | 合并状态 | 做 planner 决策 |
| `QuestionPlanner` | 选问题 | 重新解释输入 |
| `TriageReplyBuilder` | 生成回复 | 修改状态 |
| `RiskStratifierWorker` | 识别风险 / 生成风险决策 | 持有风险本体 |

---

## 13. 未来重构时最应该盯住的点

如果以后继续拆模块，最重要的不是“名字是否更细”，而是：

- 读写权限有没有变
- truth 是否被压回单一持有层
- parser 是否真的只负责 parser
- reducer 是否真的只负责归约
- planner 是否真的只消费稳定态

---

## 14. 一句话总结

模块职责图的关键不是列类名，而是明确每个类的“职责边界、输入、输出、禁区”是否真的被守住。
