# 00-总纲

## 目标

这份总纲回答一个问题：为什么 triage v2 当前不能继续沿着“哪里坏了补哪里”的方式演进，而必须先把结构拍板。

当前系统已经出现典型信号：
- 腹痛链在局部修补下大致可用
- 胸部风险链暴露出更深层的边界问题
- `TurnUnderstandingWorker` 已经承担了远超“回合理解”范围的职责
- complaint、correction、risk、planner 之间没有稳定的 source of truth

如果现在继续补实现而不先定结构，后续的每一次修复都会进一步加深耦合，最后又会重新长成 v1 风格的规则泥球。

---

## 一、为什么腹痛链看起来能跑，但这不代表结构健康

腹痛链目前的进展主要集中在：
- follow-up
- correction
- finalPrimaryComplaint
- slot-level correction

这类问题有一个共同特点：它们大多数仍沿着一条主诉语义主线推进。也就是说，虽然实现上已经开始发胖，但语义上还没有同时拉扯多个对象边界。

因此，局部启发式和兼容逻辑还能把结果“救回来”。

但这不等于结构没问题。它只说明：
- 当前结构还足以承受线性修补
- 还没有被迫同时面对 complaint memory、correction resolution、risk semantics、planner policy 之间的多边耦合

胸部链一旦出现，问题就不再是“多补两个关键词”，而是这些对象边界同时被拉出来了。

---

## 二、为什么胸部风险链暴露的是结构问题，不是词表问题

当前重点样本：
- `TRIAGE-EXT-V2-034`
- `TRIAGE-EXT-V2-035`
- `TRIAGE-EXT-V2-048`
- `TRIAGE-EXT-V2-049`

这批样本的难点不是某个信号识别不到，而是下面这些层同时参与：

1. 用户这一轮是否还在原主诉上说话
2. 主诉是否应延续、纠正还是替换
3. 某个风险线索只是 signal，还是已经形成可追问的 risk concern
4. planner 应该继续追问风险对象，还是回去问主诉
5. 当前风险动作已经出来时，哪些 gap 应该被 suppress，哪些不能

如果这些职责没有结构化分层，就会发生一种很典型的坏结果：
- 风险动作有了
- 但主诉对象没稳
- risk semantic object 也没稳
- planner 于是只能退回 slot-first
- 最后 unresolved risk 又掉回 `PRIMARY_SYMPTOM`

这不是词表问题，而是系统没有稳定的一等语义对象可供 planner 消费。

---

## 三、当前最危险的点：`TurnUnderstandingWorker` 已经过载

`TurnUnderstandingWorker` 当前实际上在同时做：
- LLM turn understanding 解析
- complaint fallback 提取
- complaint carry
- follow-up answer inference
- risk signal derivation
- correction phrase parsing
- correction target resolution
- intent repair
- 某些路径上的主诉覆盖

这意味着它已经不是一个“理解 worker”，而是：
- 半个 parser
- 半个 resolver
- 半个 reducer
- 半个 policy engine

这类大 worker 的问题不是“代码行数多”，而是它会让 source of truth 变得含糊：
- turn-level object 和 session-level truth 混在一起
- 本该 reducer 决定的事情提前在 worker 决定
- 本该 risk 层决定的事情被 complaint 层顺手做了

如果再继续在这里补 helper，虽然表面上像在抽象，实际上只是把复杂度藏进更多私有方法里。

---

## 四、这一轮必须先拍板的五个结构问题

### 1. primaryComplaint 的 source of truth 是什么

必须区分：
- turn-level `primaryComplaint`
- `slotState.PRIMARY_SYMPTOM`
- `history.finalPrimaryComplaint`
- complaint establish / carry / correct / replace 的责任边界

如果这一点不拍板，主诉在任何复杂风险链里都会反复抖动。

### 2. complaint memory 应该放在哪一层

必须明确：
- 它是不是 `TurnUnderstanding` 的责任
- 它是不是 reducer 的责任
- 它是不是独立 policy 的责任
- 哪些模块可以读它，哪些模块可以写它

如果 complaint memory 没有单一持有者，后面所有 correction 和 planner 策略都会漂。

### 3. correction resolution 应该如何拆

必须把 correction 拆成至少三件事：
- phrase parsing
- target resolution
- reducer consumption

否则 correction 会永远继续塞在大 worker 里，并不断侵入 complaint 与 slot state。

### 4. risk signal / risk semantics / risk action 应该如何分层

必须区分：
- signal detection
- semantic object construction
- action decision
- history persistence

否则胸部链会持续出现“动作先有了，但对象没收口”的问题。

### 5. planner 应该消费哪些对象

必须明确 planner 是：
- 基于 slotState 工作
- 还是基于 answered/corrected/risk semantic object 工作
- `suppressedGaps` 应由谁决定
- unresolved risk 为什么不应退回 `PRIMARY_SYMPTOM`

---

## 五、这轮的总体判断

### 判断 1

**session 级 primary complaint 的 source of truth 必须从 `TurnUnderstanding` 挪到 reducer 持有的 complaint memory。**

### 判断 2

**correction 不应该继续是 `TurnUnderstandingWorker` 内部一段“顺手把 target 猜出来并直接改状态”的逻辑，而应该拆成 parser + state-aware resolver + reducer applier。**

### 判断 3

**risk 不能再只有 signal 和 decision 两层，中间必须补出 risk semantic layer；planner 不能再让 unresolved risk 回退到 `PRIMARY_SYMPTOM`。**

---

## 六、总体架构方向

后续结构应收敛成下面的层次：

### Turn 层

负责“看见了什么”，不负责“session 最终真相是什么”。

这里的对象是候选、观察值、当轮语义结果。

### Reducer 层

负责“如何把当轮观察并入 session state”。

这里才是：
- complaint memory
- resolved correction
- stable slot state
- accumulated risk semantic state

### Risk 语义层

负责把 signal 组织成可追问、可持久、可决策的 risk concern。

### Planner 层

只消费稳定状态，做 askability、suppression 和 selection。

---

## 七、为什么必须增量迁移，而不是一步到位重画

虽然最终方向已经清楚，但不能第一步就大爆炸式重构，原因有三个：

1. 当前腹痛链已有一定保护价值，必须先保住
2. 当前 planner / reducer / risk 层已有部分可运行逻辑，应该借壳演进
3. 胸部链的问题虽然尖锐，但它建立在 complaint/correction source of truth 先不稳的前提上

所以迁移必须分阶段：
- 先稳 complaint memory
- 再拆 correction resolution
- 最后建立 risk semantic layer 并调整 planner 输入

---

## 八、下一步实现窗口最应该怎么开始

最合理的起步不是先碰 risk，而是先做 complaint / correction 的边界拉直。

也就是先把：
- `ComplaintCandidateExtractor`
- `FollowUpAnswerResolver`
- `CorrectionPhraseParser`

从大 worker 中抽出来，并把 complaint carry 的 session 级写入收回 reducer。

这样做的意义是：
- 后续 risk builder 有稳定主诉可读
- correction target resolution 有稳定 complaint memory 作为参照
- planner 之后改输入对象时，不会继续建立在摇摆主诉上
