# 02-核心数据与状态

## 1. 核心状态中心

### 已确认

当前代码里，`TriageContext` 是整个 triage 会话的核心状态容器。

它保存了：
- 会话标识
- 用户输入和最近一轮输入
- 对话历史
- `finalPrimaryComplaint`
- `slotState`
- `answeredSlots`
- `pendingSlots`
- `questionPlan`
- `riskAssessment`
- `riskDecision`
- `riskSignalState`
- `correctionHistory`
- `stateReducerHistory`
- `turnUnderstandingHistory`

## 2. `TriageContext` 的角色

### 已确认

`TriageContext` 不是普通 DTO，它是会话级状态底座。

它既承载：
- turn-level 中间结果
- session-level 归约结果
- 问题规划结果
- 风险判断结果

### 关键方法

- `resetTurnState()`：清空当前轮中间态
- `appendTurnUnderstanding(...)`：记录当轮理解
- `appendStateReducerResult(...)`：记录归约结果并更新主诉和风险状态
- `appendRiskDecision(...)`：记录风险决策
- `buildConversationTranscript(...)`：拼出送给模型或规则的会话文本

## 3. turn-level 与 session-level 的分界

### 已确认

- `TurnUnderstanding`：表示当前轮看到了什么
- `StateReducerResult`：表示当前轮如何并入会话状态
- `SlotState`：表示槽位层的投影状态
- `QuestionPlan`：表示当前轮要问什么
- `RiskDecision`：表示当前轮的风险动作和风险 gap

### 这条分界的实际意义

turn-level 更偏候选、观察、补全；session-level 更偏稳定、合并、归约。

## 4. `StateReducerResult` 的作用

### 已确认

`StateReducerResult` 当前包含：
- `reducedSlots`
- `complaintTruth`
- `answeredSlots`
- `pendingCandidates`
- `correctionLog`
- `accumulatedRiskSignals`

### 这说明什么

归约层已经把以下内容统一纳入一个结果对象：
- 主诉真相
- 槽位归约结果
- 已回答槽位
- 待追问候选
- 纠正日志
- 风险信号

## 5. `SlotState` 和投影关系

### 已确认

`SlotManager` 会把 reducer 结果投影回 `SlotState`。

这意味着：
- `SlotState` 是兼容层，也是 planner 的主要输入之一
- 但它不是主诉本体
- 它更多是结构化问诊的投影状态

## 6. 风险状态

### 已确认

风险状态在当前代码里主要体现为：
- `riskSignalState`
- `riskAssessment`
- `riskDecision`
- `riskDecisionHistory`

### 角色分工

- `riskSignalState`：更像风险信号积累
- `riskAssessment`：风险等级结果
- `riskDecision`：本轮风险动作和风险 gap

### 待验证

是否需要在未来将 risk semantic object 再进一步显式化，是后续 v2 可能继续演进的方向。

## 7. 主诉状态

### 已确认

`finalPrimaryComplaint` 会在 `appendStateReducerResult(...)` 中从 reducer 的 `complaintTruth` 投影出来。

这说明：
- session 级主诉真相已经由 reducer 路径承接
- `slotState.PRIMARY_SYMPTOM` 只是兼容投影之一

## 8. 规划状态

### 已确认

规划相关的核心状态包括：
- `questionPlan`
- `candidateQuestionGaps`
- `selectedQuestionGaps`
- `suppressedQuestionGaps`
- `askabilityDecisions`

这些状态由 planner 生成并写回 context。

## 9. 这套状态设计的真实特点

### 已确认

- state 是中心，不是附属
- `TriageContext` 承载了 turn / session / planner / risk 的多类信息
- reducer 和 planner 已经分层
- 但 turn understanding 内部仍有比较宽的语义协调职责

## 10. 一句话总结

当前 triage 的核心状态模型是“turn-level 观察 + session-level 归约 + planner/risk 输出”混合在一个 `TriageContext` 里管理。
