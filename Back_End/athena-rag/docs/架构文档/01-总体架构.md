# 01-总体架构

## 1. 项目中的 triage 是什么

`triage` 是当前系统里的分诊编排子系统。它负责接收用户输入，结合会话状态、结构化抽取、风险判断和问题规划，给出三类输出：

- 继续追问澄清
- 触发风险警示
- 生成分诊报告

## 2. 从代码确认到的主链路

### 已确认

当前代码的主入口与主流程是：

1. `TriageController.analyze(...)` 接收请求
2. `TriageOrchestratorServiceImpl.analyze(...)` 创建或恢复 `TriageContext`
3. `TriageStateMachine.execute(...)` 推进状态机
4. `TriageStageExecutor.executeParsing(...)` 执行 parsing 阶段
5. `TriageStageExecutor.executeValidation(...)` 执行 validation 阶段
6. `TriageStateMachine` 根据风险结果进入报告或警示
7. `TriageReplyBuilder` 生成最终回复
8. `TriageContext` 被保存到会话管理器和仓储

### 这条链路的真实意义

这不是一个单一 worker 直接输出结果的系统，而是一个**状态机驱动的分诊编排系统**。

## 3. 代码里的主要分层

### 3.1 接入层

当前已确认的接入层类：
- `TriageController`
- `TriageAnalyzeRequest`
- `TriageAnalyzeResponse`
- `ClientChatCompletionRequest`
- `VisionAnalyzeRequest`

职责：
- 接收 HTTP 请求
- 做最外层异常收口
- 对外暴露分诊和代理入口

### 3.2 编排层

当前已确认的编排层类：
- `TriageOrchestratorServiceImpl`
- `TriageStateMachine`
- `TriageStageExecutor`
- `TriageReplyBuilder`

职责：
- 恢复 / 创建会话上下文
- 推动状态流转
- 将 parsing、validation、risk、report 串起来
- 根据 action 生成回复

### 3.3 结构化理解与抽取层

当前已确认的相关类：
- `TurnUnderstandingWorker`
- `SemanticParserWorker`
- `FactExtractor`
- `TurnComplaintSemanticsCoordinator`
- `AnsweredSlotFlowCollector`
- `AnsweredSlotSemanticsAssembler`
- `ComplaintFallbackResolver`
- `SlotAnswerInferenceHelper`

职责：
- 理解当前轮输入
- 抽取症状、事实、已回答槽位
- 补主诉、纠正语义、风险信号

### 3.4 状态归约层

当前已确认的相关类：
- `StateReducer`
- `StateReducerResult`
- `SlotManager`

职责：
- 把 turn-level 结果并入 session-level state
- 维护 complaint truth、slot state、answered/pending、risk/correction history
- 将归约结果投影回上下文

### 3.5 规划与校验层

当前已确认的相关类：
- `QuestionPlanSupport`
- `QuestionPlanner`
- `SOPValidatorWorker`

职责：
- 生成候选问诊 gap
- 决定本轮是否可问、该问什么
- 在 planner 不足时做校验兜底

### 3.6 风险层

当前已确认的相关类：
- `RiskStratifierWorker`
- `RiskHeuristicHelper`
- `RiskTextSnapshotBuilder`
- `SemanticSignalResolver`

职责：
- 生成风险等级
- 构造 risk decision
- 提供硬红旗和历史兜底

## 4. 这个架构当前的实际特点

### 已确认

- 外层主链路已经清晰
- `StateReducer` 与 `QuestionPlanner` 已经是不同职责层
- `TriageContext` 是会话状态中心
- `TriageReplyBuilder` 负责最终对外文本
- 风险层和规划层都有独立实现

### 待验证

- turn understanding 内部各组件之间的边界是否还需要继续收敛
- 风险层与规划层之间是否存在更强的交叉依赖
- 某些 fallback 是否在业务上过于宽泛

## 5. 当前代码里最重要的判断

### 5.1 这是一个状态驱动系统

不是纯解析系统，也不是纯规则系统。

### 5.2 session truth 与 turn observation 不是一个东西

- turn-level 负责观察和补全
- session-level 负责归约和稳定状态

### 5.3 planner 依赖稳定状态

`QuestionPlanner` 需要消费 `slotState`、`answeredSlots`、`riskDecision`、`riskSignalState` 等稳定结果，而不是直接拿原始输入自己猜。

## 6. 一句话总结

当前 triage 架构的核心不是“有没有模块”，而是“模块之间的责任边界是否清楚”。
