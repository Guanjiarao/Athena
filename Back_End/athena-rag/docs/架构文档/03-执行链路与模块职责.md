# 03-执行链路与模块职责

## 1. 这份文档要回答什么

这份文档按**真实执行链路**展开，说明一次 triage 请求从进入系统到返回结果，具体经过了哪些类、哪些阶段、哪些状态写入点。

它的目标不是复述概念，而是把：
- 调用顺序
- 模块输入 / 输出
- 谁读什么、谁写什么
- 谁只做候选，谁决定真相

尽量按当前代码说清楚。

---

## 2. 顶层执行链路

### 已确认

一次 `/triage/analyze` 请求的主流程是：

1. `TriageController.analyze(...)`
2. `TriageOrchestratorServiceImpl.analyze(...)`
3. `TriageOrchestratorServiceImpl.loadOrCreateContext(...)`
4. `TriageStateMachine.execute(context)`
5. `TriageStageExecutor.executeParsing(...)`
6. `TriageStageExecutor.executeValidation(...)`
7. `TriageStateMachine.handleRiskAssessment(...)` 或 `handleReportGeneration(...)`
8. `TriageReplyBuilder` 生成最终回复
9. 上下文保存 / 终态保存

### 说明

这是一条典型的“状态机编排 + 分阶段执行 + 结果组装”链路，不是单个 worker 直出结果。

---

## 3. Parsing 阶段执行链

### 已确认执行顺序

`TriageStageExecutor.executeParsing(...)` 的顺序是：

1. `TurnUnderstandingWorker.execute(context)`
2. `SemanticParserWorker.execute(context)`
3. `FactExtractor.execute(context)`
4. `StateReducer.execute(context)`
5. `SlotManager.execute(context)`

### Parsing 阶段的真实目的

这一步不是单纯抽信息，而是把当轮输入逐层变成：
- turn-level 理解结果
- 结构化症状
- slot fact
- session-level 归约结果
- slot 投影状态

### Parsing 阶段输出会影响什么

这一步会直接影响：
- `latestTurnUnderstanding`
- `extractedSymptoms`
- `factHistory`
- `latestStateReducerResult`
- `slotState`
- `answeredSlots`
- `pendingSlots`
- `finalPrimaryComplaint`
- `riskSignalState`
- `correctionHistory`

---

## 4. Validation 阶段执行链

### 已确认执行顺序

`TriageStageExecutor.executeValidation(...)` 的顺序是：

1. `QuestionPlanner.execute(context)`
2. `syncMissingFieldsFromQuestionPlan(context)`
3. 必要时 `SOPValidatorWorker.execute(context)`
4. 根据缺失字段决定是否继续澄清

### Validation 阶段的真实目的

这一步是基于已经归约好的状态，判断：
- 这一轮还缺什么
- 哪些 gap 应该问
- 哪些 gap 应该抑制
- 是否需要继续澄清

### Validation 阶段的输出会影响什么

- `questionPlan`
- `missingFields`
- `pendingSlots`
- `lastAskedSlots`
- `nextAction`
- `finalReply`

---

## 5. Risk / Report 阶段

### 已确认

`TriageStateMachine` 在 validation 之后，还会进入：
- `RISK_ASSESSING`
- `REPORT_GENERATING`

### 风险阶段做什么

`RiskStratifierWorker` 会根据：
- 原始输入
- `riskSignalState`
- `slotState`
- 历史风险

生成：
- `riskAssessment`
- `riskDecision`

### 报告阶段做什么

`TriageReplyBuilder.generatePreTriageReport(...)` 会基于当前 context 生成对外报告文本。

## 6. 各模块职责拆解

### 6.1 `TriageController`

**输入**
- `TriageAnalyzeRequest`
- `ClientChatCompletionRequest`
- `VisionAnalyzeRequest`

**输出**
- `TriageAnalyzeResponse`
- `ClientChatCompletionResponse`
- `VisionAnalyzeResponse`

**职责**
- 接收请求
- 调用编排层
- 统一异常兜底
- 暴露三类对外入口

**不能做什么**
- 不能决定问诊策略
- 不能直接写 session state
- 不能做结构化理解

**已确认**
- 这是 triage 对外入口层

---

### 6.2 `TriageOrchestratorServiceImpl`

**输入**
- `TriageAnalyzeRequest`
- `TriageSessionManager`
- `TriageRepository`
- `TriageModelGateway`
- `TriageSessionProperties`
- `TriageConversationMemoryHelper`

**输出**
- `TriageAnalyzeResponse`

**职责**
- 创建或恢复 `TriageContext`
- 重置 turn 状态
- 追加最近用户输入
- 做会话历史压缩
- 调状态机执行
- 保存 context
- 保存终态 context

**不能做什么**
- 不能做具体 gap 策略
- 不能做主诉修正逻辑
- 不能自己当 planner 或 reducer

**已确认**
- 这是会话编排中心

---

### 6.3 `TriageStateMachine`

**输入**
- `TriageContext`
- 各阶段 worker

**输出**
- `TriageState`
- `nextAction`
- `finalReply`

**职责**
- 维护状态转移表
- 驱动 `PARSING / VALIDATING / RISK_ASSESSING / REPORT_GENERATING`
- 处理异常降级
- 决定终态和中断态

**不能做什么**
- 不能替代具体 worker 的解析逻辑
- 不能自己生成问诊内容
- 不能直接写业务抽取结果

**已确认**
- 它是阶段调度器，不是业务解析器

---

### 6.4 `TriageStageExecutor`

**输入**
- `TriageContext`
- parsing / validation 阶段 worker

**输出**
- parsing / validation 阶段的状态描述文本

**职责**
- 串起 parsing 顺序
- 串起 validation 顺序
- 把 planner 结果转换成 missing fields / clarification

**不能做什么**
- 不能自己发明业务规则
- 不能绕过 state machine

**已确认**
- 这是“阶段执行器”，不是策略器

---

## 7. Turn Understanding 链路

### 7.1 `TurnUnderstandingWorker`

**输入**
- `TriageContext`
- LLM service
- ObjectMapper

**输出**
- 更新后的 `TriageContext`
- `latestTurnUnderstanding`

**职责**
- 承接 turn understanding 执行链
- 把理解结果写回 context

**不能做什么**
- 不能单独承担 session truth
- 不能绕过 post processor / coordinator

**已确认**
- 它是 turn understanding 的入口壳

---

### 7.2 `TurnUnderstandingExecutionEngine`

**输入**
- `TriageContext`

**输出**
- turn understanding 解析结果

**职责**
- 组织 LLM 调用
- 提供 turn understanding 的执行入口

**不能做什么**
- 不能直接决定主诉真相
- 不能直接修改 reducer 状态

**已确认**
- 它负责执行，但不负责最终归约

---

### 7.3 `TurnUnderstandingExecutionShell`

**输入**
- `TriageContext`
- `latestTurn`
- parsed result supplier

**输出**
- `TurnUnderstanding`

**职责**
- 处理解析结果的 handoff
- 保底 fallback
- 将结果送入 post processor

**不能做什么**
- 不能自己发明业务 truth

**已确认**
- 这是很薄的包装层

---

### 7.4 `TurnUnderstandingResultHandoff`

**输入**
- `TriageContext`
- `latestTurn`
- parsed result supplier

**输出**
- `TurnUnderstanding`

**职责**
- 尝试获取解析结果
- 出错回退 fallback
- 交给 post processor

**不能做什么**
- 不能独立持有会话状态

**已确认**
- 这是一个转接层

---

### 7.5 `TurnUnderstandingPostProcessor`

**输入**
- `TriageContext`
- `TurnUnderstanding`
- fallback
- `latestTurn`

**输出**
- 规范化后的 `TurnUnderstanding`

**职责**
- 保底 intent
- 做 normalize
- 触发 complaint 语义补全

**不能做什么**
- 不能替代 reducer
- 不能最终拍 session truth

**已确认**
- 它是 turn-level 语义的后处理器

---

### 7.6 `TurnComplaintSemanticsCoordinator`

**输入**
- `TriageContext`
- `TurnUnderstanding`
- 当前文本

**输出**
- enrich 后的 `TurnUnderstanding`

**职责**
- 补主诉
- 收集 answered slots
- 装配 correction
- 生成 risk signal

**不能做什么**
- 不能直接代替 reducer
- 不能把 turn-level 协调变成 session truth 写入

**已确认**
- 这是当前 turn understanding 中最宽的语义协调点

**待验证**
- 后续是否还要继续拆细这一层

## 8. 结构化抽取链路

### 8.1 `SemanticParserWorker`

**输入**
- `TriageContext`
- `userInput`

**输出**
- `extractedSymptoms`

**职责**
- 调 LLM 抽症状
- 合并 heuristic 症状
- 过滤否定症状

**不能做什么**
- 不能写 session truth
- 不能直接决定 planner

**已确认**
- 这是症状语义抽取层

---

### 8.2 `FactExtractor`

**输入**
- `TriageContext`
- `latestUserTurn`

**输出**
- `factHistory` 追加

**职责**
- 抽取 slot fact
- 合并 heuristic fact
- 追加事实历史

**不能做什么**
- 不能直接归约 session truth

**已确认**
- 这是事实抽取层

---

### 8.3 `ComplaintFallbackResolver`

**输入**
- 原始文本

**输出**
- complaint 候选字符串

**职责**
- 为主诉提供硬编码 fallback

**不能做什么**
- 不能代替 reducer
- 不能单独决定 session truth

**已确认**
- 这是主诉启发式 fallback 层

---

### 8.4 `SlotAnswerInferenceHelper`

**输入**
- `SlotCode`
- 文本

**输出**
- `AnsweredSlotUnderstanding`

**职责**

**不能做什么**
- 不能替代 state reducer
- 不能直接写 session state

**已确认**
- 这是通用槽位答案推断器

---

### 8.5 `AnsweredSlotFlowCollector`

**输入**
- `TriageContext`
- `TurnUnderstanding`
- 文本

**输出**

**职责**
- 从 last asked / pending 里找候选槽位

**不能做什么**
- 不能替代 reducer
- 不能自己决定 session truth

**已确认**

---

### 8.6 `AnsweredSlotSemanticsAssembler`

**输出**

**职责**

- 修正 turn intent

**不能做什么**
- 不能写 session truth
- 不能替代 reducer

**已确认**

## 9. 状态归约链路

### 9.1 `StateReducer`

**输入**
- `TriageContext`
- `latestTurnUnderstanding`
- `factHistory`
- `slotState`
- 既有 reducer 结果

**输出**
- `StateReducerResult`
- 更新后的 `TriageContext`

**职责**
- 合并 turn observation
- 合并主诉
- 合并 answered slots
- 合并 corrections
- 合并风险信号
- 合并 facts
- 生成新的 reducer result

**不能做什么**
- 不能做 planner 决策
- 不能做 reply 生成

**已确认**
- 这是 session truth 归约中心

---

### 9.2 `ReducerCorrectionApplier`

**输入**
- reduced slots
- answered slots
- pending candidates
- correction log
- 当前轮 corrections

**输出**
- 更新后的归约状态

**职责**
- 把 correction 应用到状态上

**不能做什么**
- 不能自己猜 target

**已确认**
- 它是 correction 的最终消费层之一

---

### 9.3 `SlotManager`

**输入**
- `TriageContext`
- `StateReducerResult`
- `SlotState`

**输出**
- 更新后的 `SlotState`
- 更新后的 `extractedSymptoms`
- 更新后的 `answeredSlots` / `pendingSlots`

**职责**
- 投影 reducer 结果
- 补 primary symptom 兼容投影
- 保持 slot state 同步

**不能做什么**
- 不能重新定义主诉
- 不能跳过 reducer 自己改 truth

**已确认**
- 它是投影层，不是 truth 层

## 10. 规划与校验链路

### 10.1 `QuestionPlanSupport`

- `TriageContext`

- `riskSignalState`

**输出**

**职责**

**不能做什么**

**已确认**

**输入**
- `QuestionPlanSupport` 产出的候选 gap

**输出**

- 做 policy 选择

**不能做什么**

- 不能把 turn-level 候选当 session truth

**已确认**

### 10.3 `SOPValidatorWorker`

**输入**
- `TriageContext`
- `userInput`

**输出**
- `missingFields`

**职责**

**不能做什么**

## 11. 风险链路

### 11.1 `RiskHeuristicHelper`

**输入**
- `TriageContext`

**输出**
- `RiskLevel` 备选值

**职责**
- 提供硬红旗 fallback
- 提供 legacy 风险 fallback
- 提供快速升级判断

**不能做什么**
- 不能代替 `RiskStratifierWorker`

**已确认**
- 它是风险兜底工具

---

### 11.2 `RiskTextSnapshotBuilder`

**输入**
- `TriageContext`

**输出**
- 风险文本快照字符串

**职责**
- 拼接输入、slot、症状等信息
- 给风险规则和风险兜底使用

**不能做什么**
- 不能直接输出风险结论

**已确认**
- 它是风险输入视图构建器

---

### 11.3 `RiskStratifierWorker`

**输入**
- `TriageContext`
- `RiskTextSnapshotBuilder`
- `RiskHeuristicHelper`

**输出**
- `riskAssessment`
- `riskDecision`

**职责**
- 计算风险等级
- 生成 confirmed / suspected / unresolved risk gaps
- 决定风险动作

**不能做什么**
- 不能把自己变成 reply builder
- 不能越过 state 归约链路随意改主诉

**已确认**
- 它是风险分层与动作生成中心

---

## 12. 回复链路

### 12.1 `TriageReplyBuilder`

**输入**
- `TriageContext`
- `TriageModelGateway`

**输出**
- 澄清回复
- 风险警示回复
- 分诊报告

**职责**
- 根据 context 生成最终用户可见文本
- 对应三种 action：澄清、警示、报告

**不能做什么**
- 不能重新计算分诊状态
- 不能修改 session truth

**已确认**
- 它是回复生成层

---

## 13. 这条执行链里最关键的边界

### 已确认

1. **turn understanding 负责看懂当前轮**
2. **state reducer 负责把当前轮并入会话真相**
3. **question planner 负责选下一问**
4. **risk stratifier 负责算风险动作**
5. **reply builder 负责把结果说出来**

### 待验证

- turn understanding 的语义协调是否还需要继续拆细
- risk 与 planner 之间是否还会继续出现更强的耦合点

---

## 14. 一句话总结

当前 triage 的执行链路可以理解为：**turn-level 观察先进入理解链，再进入归约链，归约后的稳定状态才进入规划、风险和回复链。**
