# 第 2.1 课：从 `application.yaml` 反推系统能力边界

## 本课目标

本课的核心不是记配置项，而是学会一种真实项目阅读方法：

> 当你第一次接手一个复杂系统时，先读主配置文件，用配置反推系统边界、运行依赖和核心链路。

对于 `ragent` 而言，`bootstrap/src/main/resources/application.yaml` 就是这样一份“能力说明书”。

## 为什么先读配置，而不是先读 Service

很多人第一次看项目会直接冲进 `controller` 或 `service`，结果很快迷路。原因是：

- 类很多
- 调用链深
- 抽象层次多
- 你不知道哪些是主链路，哪些是支撑能力

配置文件的价值在于，它先告诉你：

- 这个系统依赖什么外部组件
- 它支持哪些能力开关
- 哪些模块是核心运行链路的一部分
- 作者最重视哪些工程问题

所以配置不是“杂项”，而是系统设计的外化结果。

## 一、先看最外层：这是一个对外提供 HTTP API 的 RAG 服务

从配置可以先确认几件最基础但非常重要的事实：

- 服务端口：`9090`
- 上下文路径：`/api/ragent`
- 应用名：`ragent${unique-name:}-service`

这说明它首先是一个独立部署的后端服务，而不是内嵌到别的系统里的库。

另外，应用名拼了 `unique-name`，这通常意味着作者考虑过：

- 本地多实例并行启动
- 不同环境区分实例标识
- RocketMQ producer group 避免冲突

也就是说，项目从配置层面就已经有了“多实例运行”的意识。

## 二、先建立基础设施全景：这不是一个轻量 Demo，而是完整依赖型系统

从配置可以直接看出，系统运行至少依赖这些外部组件：

### 1. PostgreSQL

用途不只是普通业务数据存储，还承担了至少一部分向量能力，因为配置里有：

- `spring.datasource`
- `rag.vector.type: pg`

这说明当前默认向量检索后端是 `pgvector`，不是 `milvus`。

### 2. Redis

用途大概率包括：

- 缓存
- 分布式锁
- 限流/并发控制
- 会话辅助状态

因为配置里同时出现了：

- `spring.data.redis`
- `rag.rate-limit`
- `rag.semaphore`
- `rag.memory`

这几个域经常都会依赖 Redis 或 Redisson。

### 3. RocketMQ

这说明系统里一定存在异步链路，而不是所有操作都同步完成。

在 RAG 场景下，最可能异步化的通常是：

- 文档上传后的解析与分块
- Embedding 计算
- 向量入库
- 知识库状态扫描

这和大纲里“异步分块流水线”的设计是对上的。

### 4. 向量数据库：PgVector / Milvus 双支持

配置里同时有：

- `milvus.uri`
- `rag.vector.type: pg`

这说明项目具备双后端能力，但当前默认走 `pg`。

这类设计很实战，因为很多团队在早期会先用 `pgvector` 快速落地，后续数据规模上来再切 `Milvus`。

这不是炫技，而是很典型的演进式架构思路。

### 5. S3 兼容对象存储

配置中是 `rustfs`，说明文档原文件不会直接塞数据库，而是：

- 原始文件放对象存储
- 文档元信息进关系库
- 分块和向量索引单独维护

这是标准工程做法。

## 三、`rag.*` 这部分是整个业务能力的核心地图

如果说 `spring.*` 是技术底座，那么 `rag.*` 就是系统业务设计最密集的地方。

### 1. `rag.vector`

这里定义了向量后端类型：

- `type: pg`

这说明项目在抽象上并不把向量库写死，而是把“向量存储”当成一个可替换实现。

你后面读源码时，应该带着这个问题找：

- 哪个接口统一了向量存储能力？
- `pg` 和 `milvus` 是如何切换装配的？
- 是否用了 `@ConditionalOnProperty`？

这就是后面第 5 课要重点看的东西。

### 2. `rag.default`

这里有两个非常关键的配置：

- `collection-name`
- `dimension: 1536`
- `metric-type: COSINE`

这不是普通参数，而是直接暴露了系统的向量检索基本假设：

- Embedding 维度是固定的
- 相似度度量采用余弦相似度
- 默认存在一套向量集合语义

尤其是 `dimension`，它必须和 Embedding 模型输出一致。也就是说：

> 向量库配置和模型配置是耦合的，但这种耦合被显式写进了配置层，而不是散落在代码里。

这是一种很好的工程化处理方式。

### 3. `rag.query-rewrite`

这里告诉你：

- 查询改写默认开启
- 改写会参考最近历史消息
- 历史截断按消息数和字符数双重控制

这说明问答主链路不是“用户问题直接检索”，而是：

- 先根据会话历史做上下文补全
- 再把改写后的问题用于检索

从实战角度讲，这类开关非常重要，因为查询改写效果通常不是稳定收益，必须能配置化关闭或调参。

### 4. `rag.rate-limit`

这里暴露出一个关键事实：

- 作者很在意并发控制
- 而且不是用网关统一限流草草处理，而是做了业务级并发约束

字段像：

- `max-concurrent`
- `max-wait-seconds`
- `lease-seconds`
- `poll-interval-ms`

这很像基于 Redis / Redisson 的分布式信号量或锁式并发控制。

为什么 RAG 系统会特别重视这个？

因为昂贵资源很多：

- LLM 调用贵
- Embedding 调用贵
- Rerank 调用贵
- 大文档处理很耗 CPU/IO

所以业务限流不是附属问题，而是主设计点之一。

### 5. `rag.memory`

这部分很值得你认真看，因为它说明系统做的是“工程记忆”，不是简单把历史消息全塞给模型：

- `history-keep-turns`
- `summary-start-turns`
- `summary-enabled`
- `ttl-minutes`
- `summary-max-chars`
- `title-max-length`

这意味着：

- 会话历史有滑动窗口
- 超过阈值后会触发摘要压缩
- 会话状态还有 TTL
- 可能还会自动生成会话标题

这套配置已经很接近实际生产设计，而不是 demo 级“历史消息 list 直接拼 prompt”。

### 6. `rag.semaphore.document-upload`

这是另一个很强的工程信号：

- 文档上传链路被单独做了并发保护
- 上传并不是“文件到了就立即无限并发处理”

这很合理，因为文档上传后面跟着的往往是：

- 文件落库
- 解析
- 分块
- Embedding
- 索引写入

每一步都可能压垮下游依赖，所以这里单独建一个上传信号量是很像真实系统的设计。

### 7. `rag.knowledge.schedule`

这一块说明系统还有定时/调度类后台任务，配置包括：

- 扫描延迟
- 分布式锁时间
- 批处理大小
- 最小扫描间隔

这通常意味着：

- 知识库文档处理并不完全依赖实时同步调用
- 有后台补偿、扫描、状态推进机制

这是企业项目常见的“最终一致性”设计思路。

### 8. `rag.mcp`

这里配置了默认 MCP server 地址。

这直接说明：

- MCP 不是“以后可能扩展”，而是已经被当成正式运行能力
- 问答链路存在工具调用接入点

也就是说，`ragent` 的定位不是纯知识问答，而是明显朝 Agentic RAG 方向在走。

### 9. `rag.search.channels`

这里非常关键。它几乎是多通道检索架构的配置化体现：

- `vector-global`
- `intent-directed`

并且每个通道有自己的参数：

- 置信度阈值
- top-k 倍数

这说明项目不是“查一次向量库就完了”，而是：

- 至少存在多个检索通道
- 每个通道有独立触发逻辑和结果规模
- 后续应该有统一融合与后处理链

这部分直接对应你大纲里的：

- 多通道检索
- 意图定向检索
- 后处理流水线

### 10. `rag.trace`

这里告诉你：

- 全链路 trace 可开关
- 错误信息截断长度可控

这说明作者已经考虑：

- 一次问答不是黑盒
- 各节点耗时、输入输出、错误都需要追踪
- Trace 本身也需要控制存储成本

这非常像生产系统，而不是教学 demo。

## 四、`ai.*` 这部分暴露了 `infra-ai` 的抽象设计

这一部分是你理解 `infra-ai` 模块的关键入口。

### 1. `ai.providers`

现在的 provider 至少有：

- `ollama`
- `bailian`
- `siliconflow`

而且每个 provider 都配置了：

- `url`
- `api-key`（部分）
- `endpoints`

这说明项目不是把模型名直接写死调用，而是先抽象 provider，再在 provider 下定义能力端点。

这是一层非常标准的适配器设计。

### 2. `ai.selection`

这里有：

- `failure-threshold`
- `open-duration-ms`

这两个字段非常像熔断器语义：

- 连续失败达到阈值后熔断
- 一段时间后再尝试恢复

也就是说，`infra-ai` 很可能不只是“轮询模型”，而是带有健康检查/故障切换机制。

这就是为什么项目大纲里会有“优先级路由 + 健康检查 + 自动降级”。

### 3. `ai.stream`

有 `message-chunk-size`，说明系统对流式输出做了粒度控制。

也就是说，流式不是简单透传，还可能在服务端做 chunk 控制、合并或拆分。

### 4. `ai.chat`

这里最值得你细看，因为它把模型路由策略直接配置化了。

你可以观察到：

- `default-model`
- `deep-thinking-model`
- `candidates`
- 每个 candidate 包含 `id/provider/model/priority`
- 某些模型带 `supports-thinking`

这暴露出几个重要设计事实：

#### 第一，业务层应该只关心“我要聊天”

至于：

- 走哪个 provider
- 用哪个具体模型
- 优先级如何
- 是否支持深度思考

这些都不应该散落在业务代码，而是统一交给路由层处理。

#### 第二，模型能力是有差异标签的

比如 `supports-thinking`，这就说明：

- 不是所有 chat model 都是等价的
- 某些场景会要求特定能力特征

这比“写个默认模型名”更成熟。

#### 第三，优先级不是简单数字排序，而是系统调度规则的一部分

如果某个高优先级模型挂了，系统应该还能降级到其他候选模型。

这就是实战里最值钱的地方：

> 业务不绑定单一模型，系统有连续可用性设计。

### 5. `ai.embedding`

这里显示：

- Embedding 也有候选模型
- 每个模型单独声明 `dimension`
- 默认模型可切换

这说明 embedding 并不是 chat 的附属能力，而是一个独立的一等能力域。

这点你以后自己设计项目时一定要学到。

因为很多人会把 embedding 写成某个 util 调用，后面几乎无法演进。

### 6. `ai.rerank`

这里更有意思，除了真实 rerank 模型，还配了一个：

- `rerank-noop`

这说明系统设计时考虑了“降级占位”能力：

- 有 rerank 时用真实模型
- 没有时也能走一个空实现，保证流程不断

这个思路非常工程化。

## 五、这份配置还暴露出一个很现实的问题：敏感信息管理

从当前配置内容能看到：

- 数据库地址
- Redis 地址
- RocketMQ 地址
- 对象存储地址
- 模型 API Key

这些都直接写在配置里。

从学习源码角度，这确实方便；但从真实项目安全角度，这通常不是推荐做法。

更合理的方式通常是：

- 本地开发用 `application-local.yaml`
- 生产环境走环境变量、密钥中心或外部配置中心
- 仓库里只保留示例值或占位符

这也是你做实战项目时要养成的习惯：

> 工程能跑是一回事，安全上线是另一回事。

## 六、读完这份配置，你现在应该已经能反推出什么？

至少能反推出以下结论：

1. `ragent` 是独立部署的 HTTP RAG 服务。
2. 它依赖 PostgreSQL、Redis、RocketMQ、对象存储、可选 Milvus。
3. 当前默认向量后端是 `pgvector`。
4. 问答链路不是简单直查，而包含查询改写、会话记忆、多通道检索、后处理和 trace。
5. AI 能力不是单模型直连，而是 provider 抽象 + 候选模型路由 + 熔断降级。
6. 文档入库链路具备并发控制和后台调度机制。
7. MCP 工具调用已经是正式能力，而不是以后再加的附属模块。

## 七、你下一步该怎么读源码

基于这份配置，我建议下一步不要直接去看所有 controller，而是优先验证三件事：

### 1. 验证向量存储抽象

去找：

- 向量存储接口
- `pg` 与 `milvus` 的两套实现
- 条件装配的入口

### 2. 验证 AI 抽象与路由

去找：

- `ChatService`
- `EmbeddingService`
- `RerankService`
- 路由/选择器/执行器相关类

### 3. 验证问答主链路入口

去找：

- 问答 API 入口
- 查询改写服务
- 检索引擎
- Prompt 组装服务
- SSE 返回链路

## 本课总结

配置文件最大的价值，不是告诉你“端口是多少”，而是帮助你快速建立：

- 系统依赖图
- 能力边界图
- 主链路猜测图
- 后续源码阅读优先级

在真实项目里，这是非常高效的切入方式。
