# 第 3 课：`framework` 基础设施层

## 一、课程信息

- **课程主题**：`framework` 基础设施层
- **课程定位**：第一阶段 · 基础认知
- **建议学习方式**：先通读本讲义，再回到源码逐个验证关键类的职责
- **对应源码模块**：`ragent/framework`

## 二、学习目标

学完本课后，你应当能够回答以下问题：

1. 为什么 `framework` 不是一个“工具类堆放区”，而是系统的运行约束层？
2. 为什么企业级项目要统一响应体、异常体系、分页配置、消息发送和线程上下文？
3. 为什么 RAG 项目对线程上下文透传、SSE、Trace 和远程异常分类的要求比普通 CRUD 项目更高？
4. `ragent/framework` 与传统微服务 `framework` 相比，有哪些明显强化点？

## 三、课前提醒

本节课不要把注意力放在“背类名”上，而要重点理解：

- 这些能力为什么必须抽到基础设施层
- 如果没有这一层，上层业务会如何失控
- 这些抽象为什么特别适合 RAG / Agent 场景

## 四、模块定位：`framework` 在整个项目里解决什么问题

`framework` 负责沉淀所有业务链路都会依赖、但又不属于具体 RAG 业务本身的公共能力。结合当前项目结构，它至少覆盖：

- Web 统一返回与异常处理
- MyBatis-Plus 持久层基础配置
- 分布式 ID
- 用户上下文透传
- RocketMQ 生产者封装
- 幂等支持
- Trace 上下文
- SSE 流式输出封装

### 如果没有 `framework`，上层会出现什么问题？

典型后果包括：

- 每个接口各自定义返回结构
- 每个 controller/service 自己 try/catch 拼响应
- MQ 发送风格不一致
- 异步线程里丢失当前用户信息
- Trace 信息无法贯穿整条问答链路
- 分页、时间字段填充、逻辑删除字段到处重复写

因此，本模块真正解决的问题不是“公共代码复用”，而是：

> **为上层业务制定统一的运行规则。**

## 五、模块内部能力分组

从当前目录结构出发，可以把 `framework` 大致分成五组能力：

### 1. 接口层统一约定

- `convention`

- `errorcode`

### 2. 上下文与链路透传

- `context`
- `trace`

### 3. 数据库基础设施

- `config`

### 4. 消息队列基础设施

- `mq`

- `idempotent`

本节课重点围绕大纲中的以下几个部分展开：

- 统一响应体 `Result<T>` 和 `Results`
- 全局异常处理体系

- MyBatis-Plus 配置与分页插件
- 用户上下文与 TTL 透传
- 与 `athena-framework` 的初步对比

## 六、统一响应体：`Result<T>` 与 `Results`

### 1. 为什么真实项目几乎都会定义统一响应体？

统一响应体的目标，不是为了“格式好看”，而是为了让整个系统的 HTTP 接口遵循同一套协议。

在 `ragent` 里，`Result<T>` 的核心字段包括：

- `code`
- `message`
- `data`
- `requestId`

其中成功码被统一定义为：

- `SUCCESS_CODE = "0"`

### 2. 统一响应体带来的工程价值

有了统一协议之后：

- 前端只需要按一种结构解析响应
- 成功和失败的返回形态一致
- 全局异常可以自动收口为标准返回格式
- `requestId` 可以作为接口级排查入口

这意味着，系统对外暴露的不是“某个接口返回了什么对象”，而是“所有接口都遵守什么响应协议”。

### 3. `Results` 为什么也要存在？

`Results` 不是可有可无的工具类，而是“统一构造入口”。

它至少提供了：

- 成功无数据
- 成功带数据
- 默认失败
- 基于异常构建失败响应
- 基于错误码和错误消息构建失败响应

如果没有这一层，项目里就会出现大量零散的：

- `new Result<>()`
- 手工填 `code/message`
- 同类错误返回不一致

### 4. 这一部分你真正该学什么？

重点不是“会不会写个 Result 类”，而是：

- 如何把接口协议从业务逻辑中抽离出来
- 如何让统一规范变成统一 API，而不是口头要求
- 为什么 `requestId` 这样的字段应该在一开始就预留出来

## 七、异常体系：为什么要区分 `ClientException`、`ServiceException`、`RemoteException`

很多项目只用一个 `RuntimeException`，最后造成所有错误都混在一起。对于真实系统来说，这种做法后患很大。

### 1. `ClientException`

表示客户端请求有问题，例如：

- 参数错误
- 请求状态不合法
- 当前用户上下文缺失

其本质是：

> **错在请求方，不在系统内部。**

### 2. `ServiceException`

表示服务端内部业务执行失败，例如：

- 业务状态不一致
- 某条内部流程不应走到这里
- 本地执行逻辑出现异常情况

其本质是：

> **错在当前服务自身的业务执行。**

### 3. `RemoteException`

表示远程依赖调用失败，例如：

- 调模型 API 失败
- 调向量库失败
- 调对象存储失败
- 调其他服务或 MCP 工具失败

其本质是：

> **当前系统依赖的外部能力出现问题。**

### 4. 为什么这种分类在 RAG 项目里更重要？

因为 RAG 项目天然远程依赖更多：

- Chat 模型
- Embedding 模型
- Rerank 模型
- 对象存储
- 向量数据库
- MCP 工具

如果不把远程异常单独分类，你根本分不清楚：

- 是自己代码错了
- 还是外部依赖挂了

### 5. 这套分类直接影响什么？

它会影响：

- 日志分类
- 告警维度
- 监控指标
- 重试策略
- 对前端暴露的错误语义

## 八、全局异常处理：`GlobalExceptionHandler`

`GlobalExceptionHandler` 的职责并不是“把所有异常 catch 掉”，而是把不同类型的错误，统一转换成标准响应协议。

### 1. 参数校验异常

通过拦截 `MethodArgumentNotValidException`，系统会：

- 提取第一个字段错误
- 返回清晰、可读的错误信息

这意味着项目更倾向于：

- 参数校验统一走注解体系
- 前端拿到友好的错误提示
- 避免默认异常文本直接暴露给调用方

### 2. 自定义业务异常

对于 `AbstractException`，系统会：

- 读取项目错误码体系
- 输出统一失败结构
- 控制日志粒度

这体现出一种成熟的处理思路：

- 排查问题要有足够信息
- 日志又不能无节制刷满堆栈

### 3. 认证鉴权异常

系统单独处理：

- 未登录异常
- 无角色权限异常

这说明权限问题也被纳入统一 Web 协议，而不是交给兜底异常统一吞掉。

### 4. 文件上传异常

系统还专门区分：

- 单个文件超限
- 单次请求整体超限

对文档上传系统来说，这种细分非常实用。

### 5. 兜底异常

最终通过 `Throwable` 兜底，保证所有未捕获异常都能以统一结构返回。

## 九、异常体系的职责边界

这一部分你应该形成一个明确分工：

### 业务层负责

- 抛出语义清晰的异常

### 基础设施层负责

- 统一转换对外返回格式
- 记录恰当的日志
- 控制错误暴露粒度

这比“每个 controller 自己写 try/catch 再拼 Result”成熟得多。

## 十、MyBatis-Plus 配置：分页与自动填充为什么适合放在框架层

在 `ragent` 中，`DataBaseConfiguration` 至少做了两件事：

### 1. 注册分页插件

项目显式指定了数据库方言：

- `POSTGRE_SQL`

这样做的价值是：

- 分页逻辑统一在底层配置完成
- 业务查询不需要重复关心分页方言
- 避免每个人自己处理分页 SQL 细节

### 2. 注册自动填充处理器

`MyMetaObjectHandler` 统一维护：

- `createTime`
- `updateTime`
- `deleted`

这样做的好处包括：

- 避免手工重复赋值
- 统一新增和更新时的字段行为
- 降低时间字段与逻辑删除字段遗漏风险

### 3. 你真正该学到的工程思想

稳定、重复、低变化的字段处理，不应该散落在业务层，而应该下沉到基础设施层统一完成。

## 十一、分布式 ID：为什么不直接依赖数据库自增

`CustomIdentifierGenerator` 使用雪花算法生成分布式 ID，而不是依赖数据库自增主键。

### 这样做的价值

- 更适合多实例部署
- 更适合异步链路与跨服务引用
- 实体 ID 不依赖单库单表的自增行为

在 RAG 系统中，分布式 ID 特别适合这些实体：

- 文档
- chunk
- trace
- 会话
- 后台异步任务

### 工程上的启发

ID 生成如果是系统级能力，就应该在框架层统一定义，而不应该让每张表、每个模块自己决定。

## 十二、RocketMQ 生产者封装：为什么业务层不该直接使用 `RocketMQTemplate`

在 `ragent` 中，作者并没有把 `RocketMQTemplate` 直接暴露给业务层，而是抽象出：

- `MessageQueueProducer`
- `RocketMQProducerAdapter`
- `RocketMQAutoConfiguration`

### 1. 业务真正关心什么？

业务通常只关心：

- 发到哪个 `topic`
- 业务 `keys` 是什么
- 这条消息在业务上的含义是什么
- 消息载荷是什么

而不应该重复关心：

- `MessageBuilder`
- Header 设置
- `MessageWrapper`
- 默认 key 生成
- RocketMQ 原生发送细节

### 2. 普通消息发送能力

统一参数包括：

- `topic`
- `keys`
- `bizDesc`
- `body`

这样有助于：

- 统一日志格式
- 统一消息包装方式
- 统一业务描述语义

### 3. 事务消息发送能力

接口还提供了：

- `sendInTransaction(...)`

这意味着项目已经考虑到：

- half 消息
- 本地事务执行
- commit / rollback
- 事务回查

这不是 Demo 级设计，而是很典型的生产级基础设施能力。

### 4. 你该学到什么？

中间件原生 API 不应该直接成为业务层编程模型，最好通过统一抽象，把“业务意图”和“底层协议细节”分开。

## 十三、用户上下文：`UserContext` 与 TTL 线程透传

`UserContext` 使用的不是普通 `ThreadLocal`，而是：

- `TransmittableThreadLocal`

这是本课里非常值得你记住的一点。

### 1. 为什么普通 `ThreadLocal` 不够？

因为 RAG 项目天然存在大量线程切换场景：

- 线程池异步任务
- 并行检索
- MQ 消费
- SSE 流式链路
- 后台调度

普通 `ThreadLocal` 在这些场景下很容易丢失上下文。

### 2. TTL 的价值是什么？

TTL 的核心作用是：

- 在线程池异步执行时透传线程上下文

也就是说，用户信息不会因为线程切换而消失。

### 3. 当前 `UserContext` 提供了哪些能力？

- `set`
- `get`
- `requireUser`
- `getUserId`
- `getUsername`
- `getRole`
- `getAvatar`
- `clear`
- `hasUser`

而且它存储的是 `LoginUser` 对象，而不是裸 `userId`。

### 4. 值得学习的设计点

1. 用对象承载用户快照，而不是零散字段
2. 上层 API 友好，常用字段可直接读取
3. `get()` 与 `requireUser()` 语义区分清晰

## 十四、Trace 上下文：为什么 `ragent/framework` 明显比普通 CRUD 框架更像 RAG 基础设施

`RagTraceContext` 维护了：

- `traceId`
- `taskId`
- `nodeStack`

并且同样基于 TTL。

### 这说明了什么？

说明作者没有把一次问答当成“一个 controller 调一个 service”，而是把它视为：

- 多节点
- 有层级
- 可能异步
- 需要完整追踪的一条执行链

### 一次典型 RAG 问答可能经过的节点

- 查询改写
- 意图识别
- 多通道检索
- 去重
- rerank
- prompt 组装
- 模型生成

如果没有 trace 上下文，后续很难回答这些问题：

- 哪一步最慢？
- 哪一步失败？
- 哪一步没有命中结果？
- 各节点之间是什么父子关系？

因此，`RagTraceContext` 虽然不是大纲的显式重点，但它非常能体现 `ragent/framework` 的 RAG 化特征。

## 十五、SSE 发送封装：`SseEmitterSender`

这个类看起来不大，但非常体现基础设施层思维。

它统一封装了：

- 默认事件发送
- 命名事件发送
- 连接关闭状态控制
- 异常关闭处理

并通过 `AtomicBoolean` 保证：

- 连接只关闭一次
- 已关闭连接不会继续发送

### 为什么它适合放在框架层？

因为 SSE 属于一种特殊的通信语义：

- 响应开始后，传统异常处理模型不完全适用
- 连接状态管理要求更严格
- 失败后的关闭逻辑需要一致

这类能力如果散落在业务 service 中，后续会非常混乱。

## 十六、与 `athena-framework` 的初步对比

从当前仓库结构可以先形成一个初步判断：

### `athena-framework`

更偏传统微服务基础设施，例如：

- 请求头到上下文的注入
- Feign 请求拦截器
- 常规上下文透传

### `ragent/framework`

除了传统基础设施之外，还明显强化了：

- RAG Trace
- SSE
- MQ 事务消息抽象
- 幂等提交 / 幂等消费
- 更适合 AI / RAG 场景的线程上下文透传

因此可以总结为：

> `athena-framework` 更像通用微服务基础设施，  
> `ragent/framework` 更像为 RAG / Agent 业务强化过的后端基础设施层。

## 十七、本课小结

本课最重要的不是记住若干类名，而是建立以下 5 个工程认知：

1. 统一响应体不是形式主义，而是接口协议统一。
2. 异常必须分类，否则客户端错误、服务端错误、远程错误会混在一起。
3. MQ、SSE、ID、MyBatis 配置都应在基础设施层收口，而不是散在业务代码里。
4. 普通 `ThreadLocal` 不够，RAG 项目的异步场景决定了必须考虑 TTL。
5. `framework` 的本质不是工具类集合，而是系统的运行约束层。
