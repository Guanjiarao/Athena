# 双智能体重构计划

## 当前进度更新（阶段一完成后）

### 已完成

1. 已将 `TriageStateMachine` 初步收缩为流程编排器，并拆出：
   - `TriageReplyBuilder`
   - `TriageStageExecutor`
2. 已将 prompt-heavy 内容抽离为独立模板：
   - `SemanticParserPromptTemplates`
   - `SopValidatorPromptTemplates`
   - `FactExtractorPromptTemplates`
3. 已补齐新链路基础骨架：
   - `FactExtractor`
   - `SlotManager`
   - `QuestionPlanner`
   - `TriageContext` 的相关承载字段
4. 当前版本已经可以通过一轮关键测试与 smoke eval 执行，具备阶段性交付能力。

### 尚未完成

1. `FactExtractor -> SlotManager -> QuestionPlanner` 还没有完整接管主流程。
2. 当前 triage 主链路仍主要依赖旧的：
   - `SemanticParserWorker`
   - `SOPValidatorWorker`
3. `SemanticParserWorker` 与 `SOPValidatorWorker` 存在 JSON 兼容解析 warning，虽然不影响测试通过，但会污染日志与评测体验。
4. 团队测试口径还需要进一步统一：旧单测可作为开发自检，但 triage 主护栏应逐步切到 eval 体系。

### 下一步执行顺序

1. 先清理 `SemanticParserWorker` / `SOPValidatorWorker` 的兼容解析 warning。
2. 再推进 `FactExtractor -> SlotManager -> QuestionPlanner` 更完整接入主流程。
3. 用新主链路刷新 triage smoke observed report。
4. 继续扩充 regression case，重点覆盖：
   - 否定表达
   - 弱肯定
   - 多轮补槽
   - 高风险红旗
   - 弱输入

## 目标

将当前 `triage` 模块从“症状抽取 + SOP 校验 + 规则补洞”的混合实现，重构为一套边界清晰、职责稳定、可维护的双智能体分诊架构。

本次重构的核心目标不是局部修 bug，而是解决当前设计上的根问题：

1. 把“理解用户这句话表达了什么”和“系统下一步该怎么问”彻底拆开
2. 把“文本表述”与“系统内部确认状态”拆开
3. 保留状态机作为流程骨架，但移除其中的语义判断职责
4. 用结构化 `Fact + Slot` 替代当前脆弱的 `Symptom + missingFields` 主导模式
5. 在不大改对外接口的前提下，重做 triage 内核

## 当前实现的核心问题

### 1. 把多轮问诊错误建模为“每轮重新解析全文”

当前实现每一轮都会把完整 transcript 拼成 `userInput`，然后重新执行：

- 语义抽取
- SOP 缺失字段判断
- 风险评估

这会导致一个根本性问题：

用户的短句回答，例如：

- `没发热`
- `右下腹`
- `今天开始的`
- `有点想吐`

本质上是对上一轮追问的补充，但系统会把它们当成新的主诉重新分析。

结果就是：

- 否定回答被当成症状
- 回答句被误判为主诉
- 多轮补槽失败
- 问诊体验机械且愚蠢

### 2. 症状对象无法承载真正的问诊语义

当前 `Symptom` 模型更像是一个轻量症状实体，适合单轮症状抽取，但不适合多轮问诊。

例如下列信息都不适合只用 `Symptom` 表达：

- `是否发热 = 否`
- `体温 = 38.2`
- `是否怀孕 = 未知`
- `持续时间 = 今天开始`
- `这轮是在回答上一轮追问`

因此系统只能依赖：

- LLM prompt 猜测
- 代码规则 contains
- 字符串字段名匹配

这导致内部状态不稳定、可维护性差、扩展成本高。

### 3. 语义理解、槽位判断、追问策略混在一起

当前 `SemanticParserWorker`、`SOPValidatorWorker`、`TriageStateMachine` 之间的职责边界不清楚：

- parser 在做症状归一和部分语义理解
- validator 在做规则判断、自然语言判断、追问字段推导
- state machine 在做回复拼装和动作决策

这会带来三个直接后果：

1. 一个模块改动会影响多个维度
2. 同一业务逻辑会分散到多个地方
3. 后续新增病种或追问策略时，只能继续堆补丁

### 4. 过度依赖代码词表兜底

当前否定识别、症状识别、补充字段判断等逻辑存在大量词表和字符串匹配。

这类规则只能作为高价值兜底，不能作为主语义引擎。否则必然陷入：

- 说法越多，词表越大
- 词表越大，维护越难
- 维护越难，误判越多

多轮医疗问诊的核心应该是：

- 模型负责语义归一
- 代码负责状态治理

而不是相反。

## 本次重构的总体原则

### 原则一：状态机保留，但降级为流程骨架

状态机适合表达 triage 的阶段推进，因此保留。

但它只负责：

- 当前在什么阶段
- 下一步进入哪个阶段
- 当前应该触发哪类动作

它不负责：

- 理解用户自然语言
- 判断某个说法是不是否定
- 推导具体缺失字段

### 原则二：引入 `Fact + Slot` 双层建模

#### Fact

`Fact` 是观测，是从用户话语中抽出来的原子事实。

例如：

- `FEVER_PRESENCE = NO`
- `BODY_PART = 右下腹`
- `DURATION = 今天开始`
- `NAUSEA_PRESENCE = YES`

它保留：

- 这轮说了什么
- 证据文本是什么
- 模型抽取的极性是什么

#### Slot

`Slot` 是结论，是系统当前确认后的问诊状态。

例如：

- `feverPresence = NO`
- `bodyPart = 右下腹`
- `duration = 今天开始`

它是问诊决策、风险评估、追问规划真正消费的对象。

一句话总结：

- `Fact` 是观测
- `Slot` 是系统确认状态

### 原则三：parser 主看 `latestUserTurn`

新的事实抽取器不再以 full transcript 为主输入。

主输入应为：

- `latestUserTurn`

辅输入为：

- `lastAskedSlots`
- `pendingSlots`
- `conversationSummary`

这样可以让 parser 关注：

- 这一轮用户到底补充了什么
- 是否在回答上一轮问题
- 是否新增了新的异常信息

而不是重新总结整段病情。

### 原则四：追问策略独立成模块

缺什么槽位，不等于下一轮该怎么问。

因此要把：

- 槽位状态判断
- 追问问题规划

拆成两个模块。

否则后续只要改：

- 一次问几个问题
- 什么问题优先
- 是否插入高风险红旗问题

都会污染状态管理逻辑。

### 原则五：内部重构彻底做，对外接口尽量兼容

本次重构优先重做内部核心，而不是同时推动 controller / 前端联动改造。

对外尽量保留：

- `TriageAnalyzeRequest`
- `TriageAnalyzeResponse`
- `ASK_CLARIFICATION / TRIGGER_WARNING / GENERATE_REPORT`
- `sessionId`

这样可以把改造风险控制在 triage 内部。

## 目标架构

新的 triage 内核建议拆成六个核心模块。

### 1. TriageStateMachine

职责：

- 只负责流程推进
- 不处理自然语言语义
- 不处理字段规则细节
- 不直接扫描原始文本做业务判断

建议状态：

- `INIT`
- `FACT_EXTRACTING`
- `SLOT_MERGING`
- `ACTION_PLANNING`
- `RISK_ASSESSING`
- `REPORT_GENERATING`
- `COMPLETED`
- `INTERRUPTED`

建议状态流：

1. `INIT`
2. `FACT_EXTRACTING`
3. `SLOT_MERGING`
4. `ACTION_PLANNING`
5. 若信息不足：`INTERRUPTED`
6. 若需要风险评估：`RISK_ASSESSING`
7. 低风险：`REPORT_GENERATING`
8. 高风险：`INTERRUPTED`
9. 最终：`COMPLETED`

### 2. FactExtractor

职责：

- 解析最新一轮用户输入
- 识别结构化事实
- 识别肯定 / 否定 / 不确定
- 识别程度表达（如“有点”“一点点”）
- 识别是否是在回答上一轮追问

它输出的是结构化事实，而不是系统最终结论。

输入建议：

- `latestUserTurn`
- `lastAskedSlots`
- `pendingSlots`
- `conversationSummary`
- 可选：最近一轮系统追问文本

输出建议：

- `FactExtractionResult`
  - `facts`
  - `answeredSlots`
  - `newPrimarySignal`
  - `riskHints`
  - `extractorNotes`

### 3. SlotManager

职责：

- 合并历史事实与当前事实
- 归并得到当前 `SlotState`
- 处理覆盖与冲突
- 识别哪些槽已经确认
- 识别哪些槽仍待补充

它是新内核的核心事实治理模块。

以后：

- `QuestionPlanner`
- `RiskEvaluator`
- `ReplyGenerator`

都应优先依赖 `SlotState`，而不是直接依赖用户原话。

### 4. QuestionPlanner

职责：

- 根据当前主诉和槽位状态决定下一轮追问
- 决定一次问几个问题
- 排序优先级
- 识别哪些是基础槽位、哪些是高风险红旗槽位
- 生成结构化追问计划

它不负责最终中文文案，只负责：

- 接下来问哪些槽
- 这些槽的顺序
- 为什么优先问这些槽

输出建议：

- `QuestionPlan`
  - `nextSlotsToAsk`
  - `pendingSlots`
  - `priorityReason`
  - `askCount`

### 5. RiskEvaluator

职责：

- 在关键槽位足够时进行风险评估
- 优先基于 `SlotState`
- 必要时结合 `FactHistory` 作为判级证据
- 输出结构化风险结果

它不应该再直接依赖：

- 全文 transcript contains
- symptom 名称字符串硬匹配

### 6. ReplyGenerator

职责：

- 把 `QuestionPlan` 转成自然语言追问
- 把 `RiskAssessment` 转成 warning 文案
- 把当前 `SlotState` 转成最终摘要报告

这层负责“怎么说”，而不是“该问什么”。

## 目标数据模型

### 1. TriageContext

新的 `TriageContext` 建议保留现有会话与审计字段，同时替换核心语义字段。

建议字段：

- `sessionId`
- `latestUserTurn`
- `conversationSummary`
- `conversationHistory`
- `currentState`
- `slotState`
- `factHistory`
- `lastAskedSlots`
- `pendingSlots`
- `riskAssessment`
- `nextAction`
- `finalReply`
- `stateLog`
- `auditTrail`

兼容层可临时保留：

- `extractedSymptoms`
- `missingFields`

但这两个字段不应再是核心真相源，只作为对外兼容或过渡字段存在。

### 2. Fact

建议新增 `Fact` 模型。

建议字段：

- `FactType type`
- `SlotCode slot`
- `String canonicalValue`
- `FactPolarity polarity`
- `Double confidence`
- `String evidence`
- `Integer sourceTurnIndex`
- `String sourceText`

建议说明：

- `type` 描述这是哪类事实
- `slot` 描述它服务于哪个槽位
- `canonicalValue` 是归一后的系统值
- `polarity` 用来表达肯定 / 否定 / 不确定
- `evidence` 保留原始证据短语

例如：

- `slot = FEVER_PRESENCE, canonicalValue = NO, polarity = NEGATIVE, evidence = "没发热"`
- `slot = TEMPERATURE, canonicalValue = 38.2, evidence = "38度2"`

### 3. SlotState

建议新增 `SlotState` 作为当前问诊状态载体。

第一版先做分诊专用槽位，不追求过度抽象。

建议第一批槽位：

- `PRIMARY_SYMPTOM`
- `DURATION`
- `BODY_PART`
- `PAIN_CHARACTER`
- `PAIN_SEVERITY`
- `FEVER_PRESENCE`
- `TEMPERATURE`
- `NAUSEA_PRESENCE`
- `VOMITING_PRESENCE`
- `DYSPNEA_PRESENCE`
- `BLEEDING_PRESENCE`
- `PREGNANCY_STATUS`

每个槽建议至少有：

- `value`
- `status`
- `evidence`
- `updatedAt`

其中 `status` 建议支持：

- `FILLED`
- `MISSING`
- `UNKNOWN`
- `CONFLICTED`

### 4. QuestionPlan

建议新增 `QuestionPlan`。

字段建议：

- `List<SlotCode> nextSlotsToAsk`
- `List<SlotCode> pendingSlots`
- `String priorityReason`
- `int askCount`
- `boolean followUpMode`

### 5. RiskAssessment

可以沿用现有 `RiskLevel`，但输入与证据来源要改。

建议后续评估主要来自：

- `SlotState`
- `FactHistory`

而不是来自 `Symptom[] + transcript` 的混合推断。

## 双智能体设计

本次文档中的“双智能体”不是指两个随意串联的 LLM worker，而是两个职责明确、互相解耦的智能单元。

### 智能体 A：事实抽取智能体

职责：

- 理解这轮用户说了什么
- 识别结构化事实
- 识别肯定 / 否定 / 不确定
- 识别轻重程度
- 识别本轮是否在回答上一轮追问

输入：

- `latestUserTurn`
- `lastAskedSlots`
- `pendingSlots`
- `conversationSummary`

输出：

- `FactExtractionResult`

它不负责：

- 决定缺哪些槽
- 决定下一轮问什么
- 决定最终风险等级

### 智能体 B：问诊规划智能体

职责：

- 基于当前 `SlotState` 决定缺什么
- 决定下一轮追问什么
- 决定是否进入风险评估
- 决定高风险情况下是否中止追问转为 warning

输入：

- `SlotState`
- `pendingSlots`
- `主诉相关规则`
- `risk hints`

输出：

- `QuestionPlan`
- `ActionDecision`

它不负责重新理解用户原话。

### 两者之间的边界

智能体 A 解决的是：

> 用户这句话表达了什么？

智能体 B 解决的是：

> 系统接下来应该做什么？

这条边界必须明确，不能再回到现在这种“两个 worker 都在猜文本意思”的状态。

## 新的模块职责拆分建议

### 现有模块与目标模块映射

#### `SemanticParserWorker`

现状：

- 做语义抽取
- 做症状归一
- 做部分否定兜底

目标：

- 替换为 `FactExtractor`
- 不再只输出 `Symptom[]`
- 输出结构化 `Fact[]`

#### `SOPValidatorWorker`

现状：

- 做缺失字段判断
- 做自然语言 contains 判断
- 做追问字段推导
- 做兜底规则抽取

目标：

- 删除其“大一统职责”
- 其规则部分拆入：
  - `TriageRuleRegistry`
  - `SlotManager`
  - `QuestionPlanner`

#### `RiskStratifierWorker`

现状：

- 输入混杂 transcript 和症状对象
- 规则兜底依赖字符串匹配

目标：

- 保留概念，但收窄职责
- 改成消费 `SlotState`
- 必要时参考 `FactHistory`

#### `TriageStateMachine`

现状：

- 承担状态推进 + 追问拼文案 + 风险动作决策

目标：

- 只负责编排
- 回复文案交给 `ReplyGenerator`
- 缺槽判断交给 `QuestionPlanner`
- 语义理解交给 `FactExtractor`

## 规则系统建议

本次重构后，规则不应再散落在多个 worker 内部，而应集中管理。

建议新增：

### 1. TriageRuleRegistry

职责：

- 定义不同主诉下需要哪些槽位
- 定义哪些槽为必填
- 定义哪些槽为风险优先槽

例如：

#### 腹痛

需要关注：

- `BODY_PART`
- `DURATION`
- `PAIN_CHARACTER`
- `FEVER_PRESENCE`
- `NAUSEA_PRESENCE`
- `VOMITING_PRESENCE`

#### 胸痛

需要关注：

- `DURATION`
- `BODY_PART`
- `DYSPNEA_PRESENCE`
- `放射痛`
- `出汗`

#### 发热

需要关注：

- `TEMPERATURE`
- `DURATION`
- `寒战`
- `咳嗽`
- `皮疹`

### 2. SlotPriorityPolicy

职责：

- 在多个未填槽中决定谁优先被问
- 控制一次问几个
- 高风险主诉是否优先问红旗信号

### 3. ConflictResolutionPolicy

职责：

- 用户前后说法冲突时如何处理
- 是最近一次覆盖，还是标记冲突
- 是否在后续追问中主动澄清冲突槽

## 提示词重构建议

### FactExtractor Prompt

新的事实抽取 prompt 应强调：

1. 只分析最新用户输入为主
2. 可参考上轮系统追问与待补充槽位
3. 对症状/事实必须判断极性：
   - `YES`
   - `NO`
   - `UNCERTAIN`
4. 对程度表达做归一：
   - `MILD`
   - `MODERATE`
   - `SEVERE`
5. 若用户是在回答上一轮问题，不要把回答误判为新的主诉
6. 否定事实必须保留，不得因为是否定就丢弃

### QuestionPlanner Prompt

若后续该层也使用模型辅助决策，则 prompt 应强调：

1. 你不能重新解释用户原话
2. 你只能基于当前槽位状态决定下一步策略
3. 一次最多问固定数量的问题
4. 优先覆盖主诉最关键的必要槽位
5. 高风险信号优先

### ReplyGenerator Prompt

若回复层使用模型，可要求：

1. 根据结构化追问计划生成自然中文
2. 不重复已经确认过的信息
3. 对否定信息做自然承接
4. 在追问模式下语言简洁、口语化
5. 在 warning 模式下明确就医建议但不下诊断结论

## 对外兼容策略

虽然内部将彻底重构，但建议第一版仍兼容现有外部返回结构。

### 保留

- `TriageAnalyzeRequest`
- `TriageAnalyzeResponse`
- `action`
- `message`
- `sessionId`
- `riskLevel`

### 过渡映射

为了兼容前端或调用方，可暂时从 `SlotState` 派生：

- `missingFields`
- `extractedSymptoms`

但必须明确：

- 这两个字段是“兼容映射层”
- 不是新架构的真相源

这样后面即使彻底移除旧字段，也不会影响内部设计纯度。

## 测试策略

本次重构完成后，测试重心必须从“状态流有没有走通”转向“多轮问诊行为是否正确”。

### 一、FactExtractor 测试

验证以下能力：

- `没发热` -> `FEVER_PRESENCE = NO`
- `有点发热` -> `FEVER_PRESENCE = YES` + 轻度
- `今天开始的` -> `DURATION = 今天开始`
- `右下腹疼` -> `BODY_PART = 右下腹`
- `有点想吐` -> `NAUSEA_PRESENCE = YES`

### 二、SlotManager 测试

验证以下能力：

- 当前轮事实能正确更新槽位
- 否定回答会填充槽位而不是被忽略
- 冲突时标记或覆盖符合策略
- `pendingSlots` 计算正确

### 三、QuestionPlanner 测试

验证以下能力：

- 腹痛场景优先问部位和持续时间
- 已回答 `FEVER_PRESENCE = NO` 后不再追问体温
- 高风险主诉优先插入红旗问题
- 一次追问数量符合策略

### 四、RiskEvaluator 测试

验证以下能力：

- 胸痛 + 呼吸困难 -> 高风险
- 腹痛 + 呕吐 + 发热 -> 中高风险
- 信息不足时不误判高风险，但必要时维持保守策略

### 五、整链路行为测试

必须覆盖这些关键多轮场景：

#### 场景 1：标准补槽

- 用户：`肚子疼`
- 用户：`右下腹`
- 用户：`今天开始的`
- 用户：`没发热`

期望：

- 不把 `没发热` 抽成 `发热`
- `FEVER_PRESENCE` 应为 `NO`
- 不再追问 `体温`

#### 场景 2：轻度肯定

- 用户：`有点发热`

期望：

- `FEVER_PRESENCE = YES`
- 程度为轻度或等价表达

#### 场景 3：高风险识别

- 用户：`胸口痛，还有点喘不过气`

期望：

- 快速进入 warning 分支
- 不再机械追问普通基础槽位

#### 场景 4：极弱输入

- 用户：`不舒服`

期望：

- 系统承认信息不足
- 优先追问主诉与持续时间
- 不乱抽主诉

## 施工顺序

虽然本次重构不是“边修边补”的渐进式改造，但实现上仍需遵循合理施工顺序。

### 第 1 步：定义核心模型

优先落地：

- `Fact`
- `FactType`
- `FactPolarity`
- `SlotCode`
- `SlotStatus`
- `SlotState`
- `QuestionPlan`
- `ActionDecision`

这是本次重构最关键的一步。

### 第 2 步：重写 TriageContext

把新的会话状态容器搭起来：

- `latestUserTurn`
- `factHistory`
- `slotState`
- `lastAskedSlots`
- `pendingSlots`

### 第 3 步：改造状态机骨架

让状态机切换为调用新模块，不再依赖旧 worker 的混合逻辑。

### 第 4 步：实现 FactExtractor

先把最新输入转结构化事实的能力打通。

### 第 5 步：实现 SlotManager

确保事实归并成槽位状态的规则稳定。

### 第 6 步：实现 QuestionPlanner

把“缺什么”和“怎么问”彻底分开。

### 第 7 步：接入 RiskEvaluator

把风险评估输入切到 `SlotState`。

### 第 8 步：接入 ReplyGenerator

把追问 / warning / report 的用户文案统一收敛到一层。

### 第 9 步：兼容旧接口输出

在最后阶段做：

- `SlotState -> missingFields`
- `SlotState / FactHistory -> extractedSymptoms`

这样旧接口仍可继续工作。

## 不做的事情

本次重构明确不做以下内容：

1. 不追求一开始就做成完全通用的 slot framework
2. 不试图保留旧 worker 的全部内部逻辑
3. 不把所有语义都改成代码规则
4. 不同时重构 controller / 前端协议
5. 不在新架构里继续以 `Symptom[]` 作为核心状态

## 成功标准

这次重构完成后，至少要满足以下标准：

### 架构标准

- 模块边界清楚
- 语义理解与决策规划解耦
- 问诊状态由 `SlotState` 主导
- 状态机只做流程骨架

### 行为标准

- 否定回答不会被当成新主诉
- 多轮回答能稳定补槽
- 已回答字段不会被反复追问
- 风险评估不再依赖全文本字符串乱扫

### 可维护性标准

- 新增一个主诉规则时，不需要同时改多个 worker
- 新增一个追问优先级策略时，不需要改状态管理逻辑
- 新增一个槽位时，改动范围清晰、可控

---

## 最终结论

当前 triage 模块的问题不是某几个 if 写得差，而是：

> 它把“语言理解”“问诊状态”“追问策略”“风险决策”缠在了一起。

因此本次重构的本质不是修补，而是重新建立边界。

新的双智能体架构应当明确成：

- 智能体 A 负责理解用户当前这句话表达了什么，输出 `Fact`
- 智能体 B 负责基于当前 `SlotState` 决定系统下一步做什么，输出追问计划或风险动作

只有这样，triage 模块才能真正从“词表补丁系统”升级成“可维护的多轮分诊系统”。
