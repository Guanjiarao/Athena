# 开发双智能体1

## 本阶段完成了什么

### 1. 拆分了过长的 triage 实现文件

为了让主链路更清晰、后续更容易继续做双智能体重构，这一阶段先做了职责拆分，而不是激进改行为。

已完成拆分：

- `bootstrap/src/main/java/com/nageoffer/ai/ragent/triage/engine/TriageStateMachine.java`
  - 保留状态流转与状态决策主干
- `bootstrap/src/main/java/com/nageoffer/ai/ragent/triage/engine/TriageReplyBuilder.java`
  - 承接澄清回复生成
  - 承接高风险警告回复生成
  - 承接报告 prompt 拼装与 fallback report
- `bootstrap/src/main/java/com/nageoffer/ai/ragent/triage/engine/TriageStageExecutor.java`
  - 承接 parsing / validation 阶段的执行细节

目标是把 `TriageStateMachine` 收缩成“编排器”，而不是继续做一个大杂烩类。

### 2. 把 prompt-heavy worker 的提示词抽到了独立模板文件

已新增：

- `bootstrap/src/main/java/com/nageoffer/ai/ragent/triage/prompt/SemanticParserPromptTemplates.java`
- `bootstrap/src/main/java/com/nageoffer/ai/ragent/triage/prompt/SopValidatorPromptTemplates.java`
- `bootstrap/src/main/java/com/nageoffer/ai/ragent/triage/prompt/FactExtractorPromptTemplates.java`

并完成了对应接线：

- `SemanticParserWorker`
- `SOPValidatorWorker`
- `FactExtractor`

这些类不再内嵌大段提示词文本，后续调 prompt、做 A/B、加版本管理会更方便。

### 3. 为双智能体方向补了新的基础 worker / 数据流骨架

这一阶段已经把下一步双智能体链路会用到的一些组件和上下文骨架补起来：

- `FactExtractor`
- `SlotManager`
- `QuestionPlanner`
- `TriageContext` 的相关承载字段

当前这些能力已经具备基础形态：

- 从最新用户输入提取事实
- 把事实归并为槽位状态
- 根据槽位缺失情况规划下一轮追问

### 4. 保留了当前可运行主链路

这次不是纯重构文档，而是保持了项目当前可运行。

我本地已跑过一轮关键测试：

```bash
cmd /c "mvnw -pl bootstrap -am -Dtest=TriageStateMachineTest,TriageOrchestratorServiceImplTest,TriageEvalRunnerTest -Dsurefire.failIfNoSpecifiedTests=false test"
```

结果为 `BUILD SUCCESS`。

## 本阶段没有完成什么

### 1. 还没有彻底切成“新双智能体主链路”

虽然基础骨架已经补好，但当前主状态机仍然主要走的是旧链路语义：

- `SemanticParserWorker`
- `SOPValidatorWorker`
- `RiskStratifierWorker`
- `Report generation`

也就是说：

- 新的 `FactExtractor -> SlotManager -> QuestionPlanner` 方向已经铺路
- 但还没有完全替代旧 parsing / validation 主流程

### 2. 还没有把所有 heuristic 完整下沉到更细的 helper

目前仍有一部分启发式规则留在：

- `FactExtractor`
- `SemanticParserWorker`
- `SOPValidatorWorker`

它们已经比之前清晰很多，但还没拆到最细。

### 3. 日志还不够干净

当前测试虽然通过，但仍存在一类兼容解析 warning：

- `SemanticParserWorker` 在兼容对象 / 数组结构时会打印 JSON 解析告警
- `SOPValidatorWorker` 在兼容数组 / 对象结构时也会打印类似告警

这类 warning 目前不影响测试通过，但后续应该进一步处理，减少噪音。

### 4. 还没有完成真正意义上的“双智能体策略编排”

这阶段更准确地说是：

- 完成了双智能体改造前半段的工程整理
- 给后面的双智能体执行链路腾出了结构空间

还没有完成的部分包括：

- 双智能体之间的职责边界最终落定
- 新主链路全面接管
- 更完整的回归评测与人工体验校准

## 怎么测试

建议按三层测试。

### 一、先跑核心自动化测试

在项目根目录执行：

```bash
cmd /c "mvnw -pl bootstrap -am -Dtest=TriageStateMachineTest,TriageOrchestratorServiceImplTest,TriageEvalRunnerTest -Dsurefire.failIfNoSpecifiedTests=false test"
```

关注点：

- 最终是否 `BUILD SUCCESS`
- `TriageStateMachineTest` 是否通过
- `TriageOrchestratorServiceImplTest` 是否通过
- `TriageEvalRunnerTest` 是否通过

### 二、看 smoke eval 报告

执行：

```bash
cmd /c "mvnw -pl bootstrap -am -Dtest=TriageEvalRunnerTest -Dsurefire.failIfNoSpecifiedTests=false test"
```

然后查看：

- `resources/eval/outputs/triage-smoke-report.md`
- `resources/eval/outputs/athena-rag-smoke-report.md`

重点看：

- 信息不足时是否返回 `ASK_CLARIFICATION`
- 高风险时是否返回 `TRIGGER_WARNING`
- 信息充分且低风险时是否返回 `GENERATE_REPORT`
- 风险等级是否符合预期
- 澄清语句是否自然
- 报告输出是否还能正常生成

### 三、手工挑 3 类输入做体验测试

#### 1. 信息不足

输入示例：

```text
我有点不舒服
```

预期：

- 返回 `ASK_CLARIFICATION`
- 不直接出报告
- 会继续追问主诉 / 持续时间等

#### 2. 高风险

输入示例：

```text
胸口痛，喘不过气，已经两个小时了
```

预期：

- 返回 `TRIGGER_WARNING`
- 风险等级高
- 不进入正常报告流

#### 3. 可出报告

输入示例：

```text
右下腹疼一天了，有点恶心，没有发热，按压更疼
```

预期：

- 如果信息足够，返回 `GENERATE_REPORT`
- 报告中能体现主诉、部位、持续时间、伴随症状
